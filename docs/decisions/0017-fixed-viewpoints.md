# 0017 고정 시점 8곳을 정하는 규칙

- 상태: 승인
- 날짜: 2026-10-07
- 결정한 사람: 작업자 제안 → 감독 승인(PR #3 검토, 2026-10-07)

## 맥락
P0.2. 모든 측정(기준 방식·native·browser·server)은 같은 시점에서 해야 비교가 공정하다. 시점은 사람이 손으로 찍지 않고
데이터에서 규칙으로 뽑아 다른 데이터셋에도 같은 방식으로 만들 수 있어야 한다. 이전 리포의 시점 8곳은 다른 좌표계(앱 정규화 틀)와
다른 데이터(3DGS)라 그대로 쓰지 않는다.

## 선택지
| 선택지 | 장점 | 단점 |
|---|---|---|
| 손으로 고른 시점 | 보기 좋은 장면 | 재현·다른 데이터셋 적용 불가, 고른 사람 편향 |
| **경계 상자에서 규칙으로 유도** | 재현 가능, 어떤 데이터셋에도 적용 | 장면 특징(건물 정면 등)을 모른다 |
| 무작위 시점 N 개 | 편향 없음 | 시드 관리, 빈 화면 시점이 섞임 |

## 결정
마지막 스냅샷(`flight-01` 은 event_14) 하나로 시점을 만들고 모든 이벤트·모든 구현에서 같은 시점을 쓴다.

1. 경계: 축마다 1 %·99 % 분위(떠도는 점 몇 개가 시점을 옮기지 않게).
2. 중심 c = 경계 중심, 반지름 R = 경계 대각선의 절반, 거리 d = R / sin(fov_y / 2) — 경계 구가 세로 시야에 꼭 맞는 거리.
3. 카메라: fov_y 50°, 1920×1080(결정 0007 과 같은 해상도). 위 방향 +z(ENU), 바로 위에서 볼 때만 +y(북).
4. 시점(방위는 북에서 시계 방향, 고도는 지평선에서 위로):

| 이름 | 목표 | 방위 | 고도 | 거리 |
|---|---|---:|---:|---:|
| overview_sw | c | 225° | 45° | d |
| north | c | 0° | 30° | d |
| east | c | 90° | 30° | d |
| south | c | 180° | 30° | d |
| west | c | 270° | 30° | d |
| top_down | c | — | 90° | d |
| low_south | c | 180° | 10° | d |
| close_dense | 점이 가장 많은 2 m 복셀 중심 | 135° | 35° | 0.25 d |

`close_dense` 는 가까이서 많은 점을 그릴 때(필레이트·과그리기)를 재기 위한 시점이다.

5. 검사: CPU 투영으로 각 시점에서 화면 안 점 비율 ≥ 1 %, 64×36 거친 격자 덮임 ≥ 5 % 이어야 한다.
   렌더러가 아직 없으므로 캡처 대신 이 투영 검사로 "점이 화면에 들어온다" 를 확인한다. 실제 캡처 확인은 P0.4(three.js)·P1.3(PointBlitz)에서 한다.

## 대가
- 넓은 시점 7곳은 장면이 화면의 10~23 % 만 덮는다(구가 세로 시야에 맞도록 잡아 여유가 있다). 그리기 비용의 대부분은 점 수가 정하고,
  화면을 꽉 채우는 경우는 `close_dense` 가 맡는다.
- 마지막 스냅샷 기준이라 초반 이벤트(점이 적고 원점이 다름)에서는 장면이 화면 한쪽에 작게 보일 수 있다. 이벤트 반영 시간·프레임 시간
  비교에는 문제없지만 화질 비교는 마지막 스냅샷에서 한다.
