# 0026 청크 전달 프로토콜과 native 재생 클라이언트 (P1.4)

- 상태: 제안
- 날짜: 2026-10-07
- 결정한 사람: 작업자(제안) → 감독 검토
- 관련: SPEC §3.3, 결정 0008(무압축 GPU 청크), 0009(preview 추가·refined 교체), 0018(재생 서버), 0020(측정), 0022(청크 형식)

## 맥락
P1.4 는 `pointblitz-native` 가 재생 서버를 따라 14 이벤트를 그리는 것이다. 서버가 PLY 를 청크로 바꿔 보내야 하고(SPEC §3.3),
preview 는 새 점만 보내야 한다(결정 0009). 이를 위한 HTTP 경로, 세대 번호, 클라이언트 구조를 정한다.

## 선택지와 결정
| 항목 | 선택지 | 고른 것 | 이유 |
|---|---|---|---|
| 경로 | 이벤트에 청크를 실어 보냄 / **`GET /chunks/<seq>?have=<세대>.<점 수>`** | 후자 | 기준 방식과 같은 "SSE 알림 → 클라이언트가 받으러 감" 구조라 비교가 같다. `have` 로 서버가 무엇을 보낼지 정한다(서버가 클라이언트 상태를 기억하지 않음) |
| 전달 종류 | — | 전체: 모든 점, 새 세대. 차분: 클라이언트가 가진 점 수 다음부터, 클라이언트 세대에 추가 | 차분은 그 스냅샷이 preview 이고, 클라이언트 세대가 시작된 스냅샷부터 이번 것까지 모두 "앞 스냅샷을 그대로 품은" preview 이며, 점 수가 직전 스냅샷과 같을 때만. 아니면 전체(늦게 들어온 클라이언트, 놓친 이벤트도 안전) |
| 세대 번호 | 0 부터 세기 / **전체 전달을 만든 스냅샷 번호(seq)** | seq | 늘어나기만 하고, 서버가 클라이언트별 상태 없이 정할 수 있다 |
| 응답 몸통 | 길이 표시 / **청크를 이어 붙여 만들어지는 대로 스트리밍(Content-Length 없음, Connection: close)** | 스트리밍 | 첫 청크가 변환 끝을 기다리지 않는다. 청크마다 헤더에 점 수가 있어 경계를 안다 |
| 전달 끝 | 연결 끝 / **마지막 청크의 `LAST` flag** | flag | 차분에도 `LAST` 를 붙인다(같은 세대라 Scene 은 추가로 처리 — 결정 0024 와 충돌 없음). 남은 점이 없어도 빈 청크 하나를 보내 끝을 알린다. `index` 는 전달 안의 순서 |
| 변환 시점 | 서버 시작 때 미리 / **요청 때** | 요청 때 | 변환 비용이 클라이언트의 측정 구간(받음 → 표시) 안에 들어간다. 기준 방식이 해석 비용을 내는 자리와 같다 |
| "앞 스냅샷을 품었나" 판정 | 요청마다 바이트 비교 / **서버 시작 때 한 번 바이트 비교(`is_prefix`), 스냅샷 메타데이터로 취급** | 시작 때 | 만드는 쪽(skyrecon)은 자기가 점을 덧붙였는지 안다. 요청마다 65 MB 파일 둘을 비교하면 43 ms 가 들었는데, 이는 벤치 서버의 사정이지 제품 경로가 아니다 |
| HTTP 클라이언트 | reqwest·ureq / **std `TcpStream` 직접(약 60 줄)** | 직접 | 서버도 std 로 직접 썼다(결정 0018). 루프백 고정, 의존성·비동기 런타임 없음 |
| 스레드 | 하나 / **이벤트 스레드 + 받기 스레드 + 창 스레드** | 셋 | 받는 중에도 다음 이벤트의 도착 시각을 바로 찍는다. 청크는 winit `EventLoopProxy` 로 창 스레드에 넘겨 바로 GPU 에 올린다 |
| 창·표시 | — | winit 0.30.13(Apache-2.0), wgpu 표면, sRGB 아닌 형식(색 그대로, 결정 0024), vsync 기본(결정 0021), 매 프레임 그림(기준 방식의 rAF 루프와 같게) | |
| 표시 시각 | — | 스냅샷의 마지막 청크가 Scene 에 들어간 뒤 첫 프레임에서 제출 → `PollType::Wait` → `presented` (스냅샷마다 한 번 동기화, 결정 0020) | |
| 기록 | — | `--marks` JSONL, 기준 방식과 같은 이름(`snapshot_received`, `submitted`, `presented`) + `first_chunk`, `delivered`(바이트·종류·받기 ms), `uploaded`(점·GPU 바이트), `scene_swap`, `frames` | P1.5 집계용 |

## 결과 (이 PC, RTX 4070 Vulkan, 루프백, vsync 켬 — 확인용 1 회, 측정은 P1.5)
`replay` ×60: 14 이벤트 모두 표시, 마지막 화면 2,502,015 점, GPU 정점 버퍼 40,032,240 B(16 B/점).

| seq | 종류 | 전달 | 바이트 | 받음 → 표시 |
|---:|---|---|---:|---:|
| 1 | preview | 전체 | 2,424,240 | 113.0 ms |
| 3 | preview | 차분 | 567,552 | 48.7 ms |
| 13 | preview | 차분 | 345,856 | 58.8 ms |
| 14 | refined | 전체 | 40,033,040 | 219.4 ms |

`cold` 3 회: 223.9 / 235.8 / 265.2 ms. preview 의 PLY 는 4.1~65.5 MB 인데 차분은 0.35~0.87 MB 다.

서버 로그에서 차분 전달 시간의 대부분(25~37 ms)은 차분에 필요 없는 앞부분까지 파일 전체를 읽는 데 쓰였다. 줄이는 일은 P1.5 에서 측정과 함께 한다(목표를 보고 고치지 않도록, 고친 것과 이유를 따로 적는다).

## 대가
- 서버가 요청마다 변환하므로 동시에 여러 클라이언트가 오면 변환이 반복된다. 제품 서버는 변환 결과를 캐시해야 한다(P3/P4 에서).
- 프레임마다 그리므로 정지 화면에서도 GPU 를 쓴다(기준 방식과 같은 조건을 위해). 측정 밖 사용에는 요청 때만 그리는 모드를 둘 수 있다.
