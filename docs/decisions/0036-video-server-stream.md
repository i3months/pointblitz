# 0036 영상 서버 구조와 전송 형식 (P3.2)

- 상태: 제안
- 날짜: 2026-10-08
- 결정한 사람: 작업자(제안) → 감독 검토
- 관련: 결정 0010(NVENC + WebSocket + WebCodecs), 0026(재생 서버 따라가기), 0035(NVENC 직접), SPEC §7.1 서버 영상 목표, PR #24 검토 중간 2건

## 맥락
`pointblitz-server` 가 재생 서버를 따라 장면을 갱신하고, 영상 프레임을 WebSocket 으로 보내고, 클라이언트 입력을 받아야 한다(P3.2). P3.3 의 브라우저 클라이언트와 P3.4 측정이 이 형식을 쓴다.

## 선택지와 결정
| 항목 | 선택지 | 고른 것 | 이유 |
|---|---|---|---|
| 재생 따라가기 | 서버 전용 구현 / **native 와 같은 클라이언트** | 같은 것: `pointblitz-native` 의 `net.rs` 를 `pointblitz-io::client` 로 옮김. **기본 꺼진 cargo 기능 `client` 뒤에** 두고(`serde_json` 도 그 기능에만), native·server 만 켠다 — core 는 io 에 의존하므로 기본으로 들어가면 core 의 트리에 네트워크 코드가 들어온다(SPEC §3.1, 결정 0003, PR #26 검토 H1). `scripts/check.sh` 가 `cargo tree -p pointblitz-core` 에 serde_json·tungstenite·winit·wasm-bindgen 이 없는지 확인한다 | 전달 경로(전체·차분, 결정 0026)와 시각 기록을 두 대상이 똑같이 쓴다. 중복 코드 없음 |
| 프레임 주기 | 바뀔 때만 / **고정 60 fps** | 고정 | 영상은 화면 주기마다 새 프레임이 와야 "프레임 빠짐"(SPEC §7.1)을 정의할 수 있다. 바뀐 것이 없으면 P 프레임이 수십 바이트라 비용이 작다. 늦은 틱은 몰아서 따라잡지 않는다 |
| 렌더 → 인코더 | — | `Headless::capture`(렌더 + 읽기) → `Encoder::encode` | P3.1 그대로. 공유 메모리 경로는 P3.4 에서 복사가 크면(결정 0035) |
| WebSocket | 손으로 구현 / **`tungstenite` 0.30(MIT OR Apache-2.0, `handshake` 기능만)** | tungstenite | 동기 API 라 std 스레드 구조와 맞고, 프레이밍·핸드셰이크를 직접 쓰지 않는다. 127.0.0.1 에만 묶는다(재생 서버와 같음) |
| 프레임 메시지 | 메타데이터를 따로 / **한 바이너리 메시지: `u32 LE 메타 길이` + JSON 메타 + H.264 액세스 단위(Annex B)** | 한 메시지 | 프레임과 메타데이터가 늘 같이 도착한다. 메타: `frame`, `idr`, `t_ms`, `render_ms`, `encode_ms`, `visible`(이 프레임에서 보이게 된 스냅샷), `snapshot`, `input`(마지막으로 반영한 입력 번호), `points` |
| 입력 | — | 텍스트 메시지 `{"id","type":"orbit"|"zoom"|"view",…}`, native 와 같은 카메라 조작. 메타의 `input` 으로 반영을 알림 | 입력 → 표시 지연(SPEC §7.1)을 입력 번호로 잰다 |
| 클라이언트 합류 | — | 다음 프레임을 IDR 로(SPS/PPS 포함) | 중간에 들어와도 바로 디코딩할 수 있다 |
| 클라이언트 송신 | — | 클라이언트마다 스레드 하나: 대기 중인 프레임을 모두 보내고 1 ms 읽기 시간 제한으로 입력을 받음. P 프레임이 앞 프레임에 기대므로 중간 프레임을 버리지 않음 | 단순함. 느린 클라이언트에서 쌓이는 문제는 P3.4 에서 보고 다룬다 |
| 시험용 | — | `--wait-for-client`: 첫 클라이언트가 붙을 때까지 재생을 따라가지 않음. `--exit-after-end <s>` | 시험·측정 클라이언트가 첫 스냅샷부터 본다 |

PR #24 검토 중간 2건도 여기서 고쳤다: `Encoder::new` 가 중간에 실패해도 만든 것만 정리(인코더를 CUDA 컨텍스트 직후에 만들고 각 핸들을 채움, `Drop` 은 null 이 아닌 것만 해제), `encode` 는 입력 버퍼 pitch < 너비×4 이면 오류. 같은 설정의 encode-test 결과가 바이트 단위로 같다(views 3,083,948 B, orbit 37,459,498 B).

## 결과 (`pointblitz-server serve --wait-for-client --exit-after-end 3` + `pointblitz-server probe`, replay ×60, 루프백)
| 확인 | 결과 |
|---|---|
| 첫 프레임 IDR | 예 |
| 프레임 번호 연속 | 1,967 프레임, 빠진 번호 0 |
| 수신 주기 | 59.96 fps, 간격 p50 16.66 / p99 20.57 / 최대 22.22 ms |
| 14 스냅샷 | 1~14 모두 `visible` 로 받음 |
| 입력 | 32 개 보냄, 모두 반영 확인. 보냄 → 반영된 프레임 받음 p50 17.78 / 최대 21.78 ms(디코딩·표시 전) |
| 비트레이트 | 평균 1.28 Mbps(대부분 정지 화면, 입력 때 움직임) |
| 서버 늦은 틱 | 2,146 틱 중 39(1.8 %) |

## 대가
- 서버의 늦은 틱 1.8 % 는 SPEC §7.1 "프레임 빠짐 ≤ 1 %"(클라이언트 기준)에 걸릴 수 있다. 원인(렌더 읽기 3.5 ms + 인코딩 3 ms 에 큰 청크 업로드가 겹치는 틱으로 추정)은 P3.4 에서 재고 판정한다.
- 서버는 Windows 전용(결정 0035). `probe` 는 어느 OS 에서나 빌드된다.

## 다시 볼 조건
- 느린 클라이언트 때문에 큐가 쌓이면 클라이언트별 IDR 재동기화나 프레임 건너뛰기를 넣는다.
- WebRTC 비교(결정 0010) 때 전송 계층만 바꾼다.
