# 0039 서버 영상 프레임 고르게 하기: 클라이언트 한 프레임 버퍼 (제품 개선)

- 상태: **승인(조건부)** — 감독, PR #37 검토(2026-10-08). 기본 buffer. 조건: P4.6 공개표 전에 적응형 다듬기로 추가 지연을 줄인다(수용 기준은 docs/ops/reviews/pr-37.md). 못 맞추면 출시 기본값은 immediate. 이전 상태: 구현·측정 끝, 감독 검토 대기
- 날짜: 2026-10-08
- 결정한 사람: 감독(제품 개선 선택), 작업자(구현 세부)
- 관련: 결정 0037(브라우저 클라이언트), 0038(측정 규칙), docs/bench/diagnostics.md P4.3, docs/notes/frame-pacing-proposal.md

## 맥락
서버 영상은 프레임을 잃지 않지만, 서버 틱과 브라우저 vsync 의 위상에 따라 "한 주기에 두 장 + 빈 주기" 가 생긴다(9 회 중 4 회 > 1 %, 최대 15.23 %). 사용자에게는 회전 중 끊김이다. 감독이 B(클라이언트 한 프레임 버퍼)를 골랐다.

## 결정(구현 세부)
| 항목 | 고른 것 | 이유 |
|---|---|---|
| 그리는 때 | 디코딩 출력 콜백에서 바로 그리지 않고 큐에 넣고, **rAF 마다 한 장** 그린다 | 그리기를 화면 주기에 맞춘다 |
| 여유분 | 큐에 **2 장이 모이면** 그리기를 시작하고, 이후 rAF 마다 머리를 한 장 그린다(한 장이 늘 여유로 남음) | 늦게 온 프레임이 있어도 여유분을 그려 빈 주기가 생기지 않는다. 여유분이 없으면(rAF 마다 있으면 그리기만) 늦은 도착 때 빈 주기가 그대로 남는다 |
| 쌓임 | 큐가 2 장을 넘으면 가장 오래된 것부터 버린다(그리지 않고 닫음) | 지연이 늘어나지 않게. P 프레임은 이미 디코딩됐으므로 그리기를 건너뛰어도 다음 프레임이 깨지지 않는다 |
| 스위치 | 페이지 `?pacing=buffer|immediate`, **기본 buffer** | immediate = 이전 동작(A/B·되돌리기) |
| 지표 | 그대로(빈 주기 비율, 입력→표시, `event_latency`). 버린 프레임 수를 `pacing_dropped` 로 함께 기록 | |

## 대가
- 입력 → 표시와 `event_latency` 가 늘어난다. 여유분 한 장 때문에 **약 한 화면 주기(≈ 16.7 ms)**. 제안서(docs/notes/frame-pacing-proposal.md)의 "평균 +8 ms" 는 여유분 없이 rAF 에 맞추는 경우의 추정이었고, 그 방식은 늦은 도착의 빈 주기를 없애지 못한다. 실제 증가는 A/B 로 재서 그대로 적는다. 목표(입력→표시 p50 ≤ 50 / p95 ≤ 80 ms, preview ≤ 80 ms) 안에 들 것으로 본다.

## 측정 계획(측정 전 고정)
- 같은 세션, orbit 5 회씩 buffer/immediate 번갈아, `bench/gpu-watch.mjs`, 시작·끝을 감독에게 알림. replay ×60 도 2 회씩(지연 확인).
- 보고: 실행별 빠짐 분포(1 % 초과 실행 수·최대), 입력→표시 p50/p95, preview/refined p50, `pacing_dropped`.
- P3.4 판정 행은 그대로 두고 "고친 뒤(B)" 행을 따로 싣는다.
- 목표에 걸리거나 효과가 부족하면 C(서버 위상 맞추기)를 다시 본다(감독 조건 ⑤).

## 다시 볼 조건
- 원격 서버에서 네트워크 지연이 더해져 입력→표시가 목표에 가까워지면 C 또는 여유분 0 을 다시 본다.

## 결과 (2026-10-08 13:15–13:21, 같은 세션, docs/bench/server-video.md §2.1)
- orbit 프레임 빠짐 5.50 % → **0.28 %**(두 장 주기 0, 1 % 초과 실행 4/5 → 0/5).
- 입력 → 표시 p50: orbit 17.5 → 33.3 ms(+1 주기), replay ×60 20.0 → **45.1 ms(+1.5 주기, 목표 50 의 여유 4.9 ms)**. preview p50 13.1 → 39.9 ms(목표 80).
- 판단을 감독에게 넘긴다(조건 ⑤): 끊김 효과는 충분하고 모든 목표 안이지만, replay 입력 → 표시의 여유가 작다. 작업자 의견: **B 를 기본으로 두고**, 큐가 여러 주기 동안 두 장으로 머물면 한 장을 버려 여유분을 줄이는 적응형 다듬기(작은 변경)를 다음 작업으로 하거나, 여유가 문제면 C 를 본다.

## 측정 중 실패(숨기지 않음)
- 첫 A/B(11:59 시작)에서 **7 번째 실행 — server video, pacing buffer, orbit, orbit-buffer-4** — 이 12:01 에 페이지 자원 로드 `net::ERR_NO_BUFFER_SPACE` 로 멈췄고, 하네스가 1 시간(기존 `waitForFunction` 제한)을 기다렸다. 그 전 6 회(orbit buffer·immediate 1–3)는 `target/bench/p39ab-aborted` 에 두고 **판정에 쓰지 않았다**(같은 세션 조건을 지키려고 14 회를 처음부터 다시 돌림).
- 다시 돌릴 때 미리 정한 규칙: 실패한 실행만 같은 조건으로 1 회 재시도, 실패한 시도의 파일은 `*.tryN-failed.*` 로 남김, 실행마다 시작 전·실패 시 127.0.0.1 소켓 상태 수를 `runs.log` 에 남김. **재측정에서 실패·재시도는 0 회**(대체한 실행 없음). 소켓 수는 내내 평상(LISTENING 13, ESTABLISHED 4 안팎).
- 원인은 가르지 못했다. 후보: (1) 반복 실행으로 소켓·포트 자원 고갈, (2) 클라이언트가 서버 송신을 못 따라가 쌓임(결정 0036 의 "느린 클라이언트" 다시 볼 조건). 오류가 영상 WebSocket 이 아니라 페이지 자원 로드에서 났으므로 (1) 쪽으로 기운다. 다시 나오면 runs.log 의 소켓 수로 가른다.
- 하네스 수정(고장을 빨리 드러내는 장치일 뿐, 원인 수정 아님): `baseline/three/run.mjs --timeout <s>`(기본 3600 그대로), `bench/video/run.mjs` 는 300 s 로 넘기고 클라이언트가 실패하면 자기 자식인 서버 프로세스를 끝낸다.
