# 0038 P3.4 측정 정의와 유효성 규칙 (측정 전에 고정)

- 상태: 승인
- 날짜: 2026-10-08
- 결정한 사람: 작업자 제안(프레임 빠짐 구간은 감독 결정) → 감독 승인(PR #28 검토, 2026-10-08)
- 관련: SPEC §7.1 서버 영상 목표(2026-10-08 소유자), 결정 0020·0032·0036·0037, PR #27 검토

## 맥락
P3.4 에서 three.js·native·browser·server video 를 같은 세션에서 번갈아 재고 서버 영상 목표를 판정한다. 측정 준비 중, 같은 PC 에서 다른 GPU 작업(원인 확인 안 됨 — *감독 정정, PR #28 검토: 처음에는 "다른 세션의 재현 실행으로 보임" 이라 적었으나, 감독의 재현은 10:39:58 에 끝났고 그 시각대 작업자 준비 실행과 겹치지 않았다. 확인된 것은 같은 시각 데스크톱 Chrome 이 새 프로세스를 띄운 것뿐이다*)이 겹친 실행에서 서버 렌더·인코딩이 2~3 배 느려졌다(늦은 틱 0.3 % → 30 %). 정의와 유효성 규칙을 **측정 전에** 고정한다.

## 측정 정의 (서버 영상)
| 지표 | 정의 |
|---|---|
| `event_latency` | 서버가 스냅샷 알림을 받은 때(WebSocket 텍스트로 즉시 전달, 결정 0037) → 그 스냅샷이 처음 보이는 영상 프레임을 브라우저가 그린 때. 다른 대상의 "클라이언트가 SSE 를 받은 때 → 표시" 와 같은 사건(PR #27 검토) |
| 입력 → 표시 | 번호 붙은 입력을 보낸 때 → 메타 `input` ≥ 번호인 첫 프레임을 그린 때(500 ms 마다, 측정 내내) |
| 프레임 빠짐(판정) | **orbit 시나리오**에서 첫 영상 프레임을 그린 뒤 ~ orbit 끝(메타 `phase` 가 `done` 인 프레임을 그리기 전)까지, 새 영상 프레임을 그리지 못한 60 Hz 주기의 비율(감독 결정). replay·cold 의 빠짐은 보고만 |
| 화질(판정) | 고정 시점 8곳: 서버 영상을 브라우저가 그린 캔버스(30 프레임 안정 뒤) 대 native 캡처 SSIM. 진단: 점 영역 SSIM(점이 있는 창만), 인코딩 전 서버 프레임 대비 |
| 메모리(기록만) | 클라이언트 렌더러 `mem_cpu`(OS 최대 commit), 서버 프로세스 `mem_server_peak`(같은 방법) |
| 서버 | 틱마다 렌더·인코딩 시간(p50/p95/p99), 예산(16.7 ms) 넘은 틱 비율 |

서버와 브라우저는 **같은 PC·같은 GPU** 를 쓴다(서버 렌더·인코딩과 브라우저 디코딩이 GPU 를 나눔). 결과에 그대로 적는다.

## 유효성 규칙 (감독 요청, PR #27 이후)
1. **실행마다 GPU 를 기록한다**: `bench/gpu-watch.mjs` 가 실행 2 초 전부터 끝까지 500 ms 마다 `nvidia-smi`(GPU·인코더 사용률, 클럭, P-state)와, 앞뒤의 GPU 프로세스 목록을 `<run>.gpu.csv` 로 남긴다.
2. **오염 기준(측정 전 고정)** — 하나라도 맞으면 그 실행은 "오염":
   - C1 실행 직전 2 초의 GPU 평균 사용률 > **15 %**(이 PC 의 빈 상태는 1~3.5 %, 준비 실행에서 확인).
   - C2(server video) 서버 렌더 p50 또는 인코딩 p50 이 같은 세션·같은 시나리오 server video 실행들의 중앙값의 **2 배** 초과.
3. 오염 실행은 판정에서 빼고 **같은 구현·시나리오를 다시 잰다**. 빼낸 실행도 숫자와 함께 `contaminated/` 에 남기고 문서에 적는다(숨기지 않음). `bench/contamination.mjs` 가 판정한다.
4. 측정 시작·끝을 감독에게 알리고, 그동안 감독은 GPU 를 쓰는 재현을 하지 않는다.

## 입력 이상치 (PR #27 검토 중간)
감독 실행의 입력 → 표시 최대 512.9 ms 는 준비 실행 5 회에서 재현되지 않았다(최대 68.3 ms). 서버 로그(`--log`)로 보면 입력 수신 → 반영 틱은 최대 20 ms 였다. 같은 시간대의 GPU 경합(위)도 원인일 수 있다. 측정 중 다시 나오면 서버 로그로 수신 전·후를 가른다.

## 적용 결과
2026-10-08 10:52~11:10 측정: 78 실행, C1·C2 오염 0. 결과는 [docs/bench/server-video.md](../bench/server-video.md).

## 대가
- 같은 PC 에서 서버와 클라이언트가 GPU 를 나누므로, 서버만 따로 둔 경우보다 서버 렌더·인코딩이 느리다(준비 실행: 렌더 p50 3.8 → 5.6~6.1 ms, 인코딩 2.8 → 5.5 ms). 서버를 다른 GPU 에 두는 측정은 V100 단계(비용 모델)에서.

## 다시 볼 조건
- 다른 장비에서 빈 상태 GPU 사용률이 다르면 C1 문턱을 그 장비에서 다시 정한다.
