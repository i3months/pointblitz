# 0037 서버 영상 브라우저 클라이언트와 디코더 지연 수정 (P3.3)

- 상태: 제안
- 날짜: 2026-10-08
- 결정한 사람: 작업자(제안) → 감독 검토
- 관련: 결정 0010(WebSocket + WebCodecs), 0020(측정 이름), 0035(NVENC), 0036(전송 형식), SPEC §7.1 서버 영상 목표

## 맥락
브라우저가 서버 영상(결정 0036)을 받아 그리고, 입력을 보내고, SPEC §7.1 의 서버 영상 지표(이벤트 반영·입력→표시·프레임 빠짐)를 남겨야 한다.

## 선택지와 결정
| 항목 | 선택지 | 고른 것 | 이유 |
|---|---|---|---|
| 디코더 | `<video>` + MSE / **WebCodecs `VideoDecoder`** | WebCodecs(결정 0010) | 프레임 단위로 제어하고 시각을 잴 수 있다. `optimizeForLatency: true`, `prefer-hardware`. 첫 IDR 의 SPS 로 `avc1.PPCCLL` 을 만든다 |
| 그리기 | rAF 에서 / **디코더 출력 콜백에서 바로 캔버스 2D 에 `drawImage`** | 콜백 | 한 주기를 기다리지 않는다. 그린 프레임은 다음 합성 때 화면에 나온다 |
| `snapshot_received` | 페이지가 재생 서버 SSE 를 따로 들음 / **서버가 받는 즉시 텍스트 메시지로 알림** | 서버 알림 | SSE 연결마다 일정이 그 연결 시각부터라, 두 연결이면 시각이 어긋난다. 실제로도 사건은 서버 쪽에서 생긴다. 그래서 서버 영상의 `event_latency` = **서버가 알게 된 때 → 브라우저에 그 스냅샷이 보이는 프레임을 그린 때**(루프백 WebSocket 전달 포함) |
| `presented` | — | 메타 `visible` 에 그 스냅샷이 처음 실린 프레임을 그린 때 | 다른 대상과 같은 뜻(그 스냅샷이 보이는 첫 화면) |
| 입력 → 표시 | — | `inputs=1` 이면 500 ms 마다 번호 붙은 orbit 입력. 메타 `input` ≥ 번호인 첫 프레임을 그린 때까지 | SPEC §7.1 정의 |
| 프레임 빠짐 | — | rAF 주기마다 "지난 주기 이후 새 영상 프레임을 그렸나" 를 세어 빠진 주기 비율(SPEC §7.1 정의 그대로) | |
| 측정기 | 새 스크립트 / **`baseline/three/run.mjs --target video --query ws=…`** | 공용 | 같은 Chrome·플래그·`summarize()`. 새 지표: `input_latency_p50/p95/max`, `input_unanswered`, `video_frame_missed_pct`, `video_decode_ms_p50/p95` |
| 서버 쪽 | — | `serve --cold`(마지막 스냅샷만) 추가 | SPEC §6.1 cold |

## 디코더 지연 수정 (기능 결함, P3.4 판정 전)
첫 실행에서 입력 → 표시 p50 86.4 ms 였다. probe(디코딩 없음)로는 반영 프레임을 17.8 ms 에 받았으므로 디코딩·그리기에서 약 70 ms(약 네 프레임)가 붙었다.
원인: 스트림에 B 프레임이 없다는 표시가 없어 디코더가 재정렬용으로 프레임을 붙잡았다. 인코더에 **H.264 VUI `bitstream_restriction`** 을 켜면(`h264VUIParameters.bitstreamRestrictionFlag = 1`, NVENC 가 `max_num_reorder_frames = 0` 을 씀) 디코더가 바로 내보낸다.
목표를 맞추려는 조정이 아니라 스트림 표시가 빠진 결함이라 P3.3 에서 고쳤고, 전후를 남긴다(같은 시나리오, replay ×60, 입력 켬, 각 1 회):

| 지표 | 수정 전 | 수정 후 |
|---|---:|---:|
| 입력 → 표시 p50 / p95 | 86.4 / 107.2 ms | 18.8 / 26.8 ms |
| `event_latency` preview p50 / refined p50 | 79.5 / 197.9 ms | 13.1 / 90.7 ms |
| 프레임 빠짐 | 4.83 % | 1.10 % |
| 서버 늦은 틱 | 113 / 2,051 | 3 / 2,088 |
| 디코딩(받음 → 출력) p50 | (재지 않음) | 0.3 ms |

## 결과 (완료 기준 확인, 이 PC, Chrome 155 헤드리스)
| | replay ×60 | cold |
|---|---:|---:|

| preview p50 | 13.7 ms | — |

| 입력 → 표시 p50 / p95 | 11.2 / 19.2 ms | 19.4 / 20.3 ms |
| 프레임 빠짐 | 1.05 % | 6.57 %(아래) |

- cold 의 6.57 % 는 약 2 초(131 프레임) 실행이라 디코더 설정·첫 프레임 전 주기가 큰 몫이다. P3.4 에서 프레임 빠짐을 재는 구간(예: 첫 프레임 뒤부터, orbit 처럼 충분히 긴 구간)을 측정 전에 정한다.
- 판정은 P3.4 에서 한다(SPEC §7.1 서버 영상 목표).

## 대가
- `presented` 는 캔버스에 그린 때이고, 실제 화면 표시는 다음 합성 주기다(다른 브라우저 대상의 GPU 완료와 같은 수준의 정의).
