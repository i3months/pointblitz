# 0051 받기 바닥을 깨기 — 좌표 16 비트 청크(④)와 정밀 스냅샷 거친 것 먼저(③)

- 상태: 승인(소유자 ③·④ 허용 2026-10-09, 감독 검토 PR #76). ④ 는 측정으로 **v2-12** 를 골랐다([chunk-v2-choice.md](../bench/chunk-v2-choice.md), P4.12)
- 날짜: 2026-10-09
- 결정한 사람: 소유자(③·④ 모두 허용, "만족할 성능이 나올 때까지 계속, 대역폭은 얼마든 늘어도 됨"), 감독(목표·측정, 측정 전 고정), 작업자(방법)
- 관련: 0008(GPU 레이아웃 무압축 청크), 0022(청크 형식 v1), 0026·0050(전달), 0049(측정 규칙), SPEC §6.2·§7.1

## 맥락(감독 진단, 2026-10-09)
- Chrome 이 40 MB 를 받는 데 메모리에서 보내는 서버에서도 69–109 ms(8 회), 4·8 개 병렬 요청도 69–98 ms 로 줄지 않는다. 0050 뒤 web 정밀 지연의 바닥은 브라우저 받기이고, **받을 바이트를 줄이는 것 말고는 이 바닥을 깨지 못한다.**
- 0008 은 "무압축, GPU 레이아웃 그대로(점당 16 B)" 를 골랐다(해석 비용 0). 좌표 양자화는 GPU 가 풀 수 있으므로 해석 비용 0 을 지키며 바이트를 줄일 수 있다.

## 결정
### ④ 청크 형식 v2 — 좌표를 청크 경계 상자 기준 16 비트로
- 좌표: 청크 머리의 경계 상자(이미 있음: 원점 f64 + 최소·최대 f32)를 기준으로 **u16×3**(0 … 65535 가 최소 … 최대). GPU 가 `최소 + q / 65535 × (최대 − 최소)` 로 푼다(정점 셰이더, 청크마다 크기 하나 더 받음). CPU 해석은 여전히 없다.
- 두 안을 만들어 고른다.

  | 안 | 점당 | 내용 | 정밀 스냅샷 14(250만 점) |
  |---|---|---|---|
  | v2-12 | 12 B | u16×3 + 채움 u16 + 색 RGBA8 | 30.0 MB(지금 40.0 MB 의 75 %) |
  | v2-8 | 8 B | u16×3 + 색 RGB565(u16) | 20.0 MB(50 %) |

  - 좌표만 16 비트로 하면 6 + 4 = 10 B 이고 정렬하면 12 B 다 — "절반" 이 아니다. 8 B 가 되려면 색도 16 비트여야 한다.
- **고르는 기준(측정 전 고정)**: 고정 시점 8 곳 SSIM(대 지금 f32·RGBA8 그림, native 캡처)과 최대 좌표 오차(mm, 모든 점에서 원래 좌표 대 푼 좌표)를 둘 다 재고, **SSIM ≥ 0.999(8 곳 모두) 를 지키는 가장 작은 쪽**을 고른다. 둘 다 못 지키면 v2-12. 최대 좌표 오차는 기록(목표 아님).
  - **실제로 보내는 청크로 잰다**(감독 검토 #76): ③ 의 순서로 나누면 정밀 전달의 청크마다 점이 장면 전체에서 뽑히므로 청크 경계 상자가 장면만큼 커지고 16 비트 간격도 커진다. 그래서 SSIM·최대 오차는 **③ 순서로 나눈 실제 정밀 전체 청크**와 **미리보기 차분 청크** 둘 다에서 잰다(마지막 스냅샷과, 그 앞 미리보기 차분). 청크마다의 장면 크기(경계 상자 변, m)와 좌표 간격(변 ÷ 65535, mm)의 최대·중앙값을 함께 싣는다.
- 모든 클라이언트(native · web WebGPU · webgl · 서버 영상의 서버 GPU)가 같은 v2 를 쓴다 — 그리기 경로가 하나로 남는다. 서버 영상은 바이트가 네트워크를 지나지 않지만 같은 변환·같은 셰이더를 쓴다(그림이 같아야 하므로).
- 같은 API 기준 B1(three.js 같은 청크 경로: B1a · B1b · B1-webgpu)도 v2 를 그대로 받는다: 좌표는 정규화된 `Uint16Array` 속성, 청크마다 `Points.position = 원점 + 최소`, `Points.scale = 최대 − 최소`(three.js 가 행렬로 푼다, CPU 해석 없음). v2-8 이면 색은 RGB565 를 셰이더에서 푼다(B1 은 `onBeforeCompile` 로 같은 식). 같은 바이트를 받으므로 같은 API 비교는 그대로 공정하다.
- 형식 버전은 머리의 `version = 2`. v1 을 읽는 클라이언트(crates.io 0.1.0)는 v2 를 거부한다(머리 검사로 오류) — 다음 배포 버전에서 형식이 바뀐다고 적는다.

### ③ 정밀(전체) 전달은 거친 것 먼저
- 서버는 전체 전달의 점을 **8 개마다 하나씩 고른 순서**로 보낸다: 원래 순서에서 번호를 8 로 나눈 나머지가 0 인 점들, 그다음 4, 2, 6, 1, 5, 3, 7(나머지의 비트 뒤집기 순). 정렬하지 않으므로 변환 비용은 늘지 않고, 앞 1/8 만으로도 장면 전체가 고르게 덮인다(skyrecon 의 점 순서는 지역적으로 이어져 있어 8 개마다 하나면 모든 곳에서 뽑힌다).
- 첫 1/8 이 끝나는 청크의 머리에 새 표시 비트 `FLAG_FIRST_PASS_COMPLETE`(bit 1)를 단다. 클라이언트는 그 청크가 도착해 올라간 즉시 **새 세대로 바꿔 그리고**(지금은 마지막 청크 뒤), 나머지 청크는 오는 대로 같은 세대에 채운다. 미리보기(차분)는 그대로다.
- 점 크기는 그대로 2 px(거친 단계에서 키우지 않는다 — 그림 규칙 SPEC §3.2 를 바꾸지 않음).
- 서버 영상: 영상 서버도 같은 순서·같은 표시로 첫 1/8 에서 새 세대로 바꿔 그린다.
- **B1(B1a · B1b · B1-webgpu)도 `FLAG_FIRST_PASS_COMPLETE` 에서 새 세대로 바꾼다**(감독 검토 #76) — 첫 반영의 같은 API 비교가 공정하려면 같은 청크·같은 바꾸는 시점이어야 한다. B2(SkyLens 식 PLY)는 청크를 받지 않으므로 그대로(완전 반영만 있음).

### SPEC 수정(소유자가 허용한 범위: 지연 정의에 '첫 반영' 추가)
- §6.2 표에 한 줄: `event_first_latency` — 이벤트 도착 → 그 이벤트의 새 세대가 **처음** 보이는 프레임(정밀: 첫 1/8 이 올라간 뒤, 미리보기: `event_latency` 와 같음) | ms. `event_latency`(그 이벤트의 점이 **모두** 보이는 첫 프레임)는 정의를 바꾸지 않는다 — "완전 반영".
- §7.1 에 목표 두 줄(감독이 정함, 측정 전 고정): **web(browser WebGPU) 정밀 `event_first_latency` p50 ≤ 50 ms**, **서버 영상 정밀 `event_first_latency` p50 ≤ 50 ms**. 기존 목표는 그대로(완전 반영 기준).
- §3.3 표의 "무압축 청크" 를 "GPU 가 그대로 쓰는 청크(좌표 16 비트, 결정 0051)" 로.
- §9 변경 기록에 한 줄.

### 측정(0049 규칙, 측정 전 고정)
- 변경 전 = 0050 병합 뒤 main(ee1609e 이후, 측정 시작 때의 main), 변경 후 = 이 결정의 구현.
- `bench/ab.sh` 로 같은 세션 번갈아: web · webgl · native · video × replay ×60 10 회 + cold 10 회, C1–C4, 부트스트랩 95 %(씨앗 48049), 비 = 전 ÷ 후.
- 지표: 완전 반영(`event_latency` 미리보기·정밀·cold, 지금과 같은 정의)과 **첫 반영**(`event_first_latency` 정밀·cold), 받은 바이트, 메인 스레드 멈춤, mem_cpu.
- 그림: ④ 고르기용 SSIM·최대 좌표 오차(위), 그리고 고른 형식으로 완전 반영 뒤 고정 시점 8 곳 SSIM(대 변경 전)을 싣는다.
- 받기 바닥(40 MB 정적 파일)을 같은 세션 시작·끝에 다시 잰다.

## 대가
- 좌표 정밀도: 청크 경계 상자 크기 ÷ 65535(측정해 싣는다). 청크는 점 순서대로 256K 점씩이라 상자가 장면만큼 클 수 있다.
- 거친 단계 동안 화면의 점이 1/8 이다(정밀 스냅샷이 다 오기 전 잠깐).
- 청크 형식 버전이 올라가 0.1.0 클라이언트와 호환되지 않는다. **다음 배포는 0.2.0** 이다(기록).

## ④ 를 고른 결과(P4.12, 2026-10-09)
- 두 안 모두 "8 곳 모두 SSIM ≥ 0.999" 를 못 지켜 고정 규칙대로 **v2-12**(v2-12 평균 0.9962·close_dense 0.9756, v2-8 0.9953·0.9735). 감독 판단: 결과를 본 뒤 기준을 바꾸지 않는다.
- 원인 나누기: 같은 데이터에서 ③ 의 그리는 순서만 바꿔도 평균 0.9954(close_dense 0.9708), 양자화만이면 0.9971 — 차이 픽셀은 99.998–100 % 가 기준 점 영역 1 px 팽창 안. 0.999 기준은 ③ 만으로도 깨지며, SSIM 이 재는 것은 겹친 점의 앞뒤·경계 1 px 이동이다.
- v2-12 화질 근거(보충): 차이가 점 경계 1 px 이동뿐(팽창 안 ≥ 99.9 %), 최대 좌표 오차 0.87 mm(상자 약 111 m, 간격 1.7 mm), 색 그대로.

## 다시 볼 조건
- **첫 반영 목표(web 정밀 ≤ 50 ms)를 v2-12 로 못 지키면 v2-8 을 다시 본다.** 그때 기준은 측정 전에 정한다: 같은 ③ 순서의 v2-12 대비, 차이 픽셀의 팽창 안 비율과 색 오차(ΔE 등)(감독 판단 2026-10-09).
- 최대 좌표 오차가 그림에 보이면(SSIM 은 넘지만 눈에 띄는 계단 등) 청크를 공간으로 나누는 것을 본다.
- 첫 반영 목표를 못 지키면 첫 단계 비율(1/8)을 바꾸는 것을 본다(그 전에 이 결정을 고친다).
