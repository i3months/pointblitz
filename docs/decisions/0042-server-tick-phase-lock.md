# 0042 서버 영상: 서버 틱을 클라이언트 화면 위상에 맞추기(phase lock)

- 상태: **위상 잠금은 끔으로 확정**(다듬기 1 회 뒤에도 수용 기준 미달 — 감독 규칙, 더 다듬지 않음). `--phase-lock on` 은 선택지. 쓰기 스레드 송신은 기본(감독 승인, PR #44)
- 날짜: 2026-10-08
- 결정한 사람: 감독(하는 것, 조건·수용 기준), 작업자(구현 세부)
- 관련: 결정 0037(브라우저 클라이언트), 0039·0040(프레임 버퍼 — 선택지로만), 0041(C4), docs/notes/server-phase-alignment-proposal.md, docs/bench/diagnostics.md P4.3

## 맥락
기본 경로(immediate)는 C1–C4 세션에서 orbit 프레임 빠짐 8.15 %(5/5 > 1 %)로 SPEC 미달이다. 프레임은 사라지지 않고, 서버 틱(60 Hz 타이머)과 브라우저 화면 갱신의 위상이 연결 때 우연히 정해져 도착이 갱신 경계 근처에 걸리면 "빈 주기 + 두 장 주기" 가 생긴다. 버퍼(0039·0040)는 지연을 더해 수용 기준을 못 맞췄다.

## 구현 중 찾은 원인 — 서버 송신 경로(2026-10-08 14:5x, 스모크 시험)
- 위상 잠금을 켜도 빠짐이 그대로였다(6.84 대 8.03 %). 클라이언트의 위상 보고가 잠금을 끈 상태에서도 0.5 초마다 크게 튀었고, 30 프레임의 위상 집중도가 0.03–0.21(거의 고르게 퍼짐)이었다 — 잠글 위상이 없었다.
- 프레임별로 보면 서버 틱 → 받은 시각이 톱니 모양이었다: 프레임마다 약 1.1 ms 줄다가 약 13 프레임마다 +15 ms 뛴다 = **프레임이 16.7 ms 가 아니라 15.6 ms 격자로 나갔다.** 클라이언트 스레드가 읽기 제한 1 ms 로 읽고 그 사이에 보냈는데, Windows 의 소켓 읽기 제한은 시스템 타이머 틱(기본 15.625 ms) 단위로 끝난다(이 프로세스는 1 ms 타이머를 요청하지 않음). P4.3 의 "도착 흔들림 p5–p95 14.5–19.1 ms" 와 위상 운의 실체가 이것이다.
- **고친 것**: 클라이언트마다 쓰기 스레드가 채널에 들어온 프레임을 바로 보내고, 읽기는 막힘 읽기로(입력·위상 보고). P4.3 에서 같은 시도가 "효과 없음" 이었던 A/B 는 결정 0041 전(C4 미상)이라 믿을 수 없었다. 이전 경로는 `serve --send poll` 로 남김(A/B 용).
- 스모크(각 1 회, C1–C4 통과): poll·잠금 끔 빠짐 7.49 %(받기 간격 변화 p95 +14.3 ms, 집중도 0.04) / 쓰기 스레드·잠금 끔 6.17 %(±2.4 ms, 0.65) / **쓰기 스레드·잠금 켬 0.79 %(0.73), 입력 → 표시 p50 27.1 ms(끔 33.6)**.

## 결정
| 항목 | 고른 것 | 이유 |
|---|---|---|
| 클라이언트가 재는 것 | 디코딩 출력 시각 t 의 화면 주기 안 위상 φ = ((t − 마지막 rAF 시각) mod P) / P, P = 최근 rAF 간격 중앙값. 30 프레임마다(0.5 s) 원형 평균 φ̄ | rAF 밖에서 그린 프레임은 다음 렌더링 갱신에 나간다 — 갱신 경계(φ ≈ 0/1)가 위험한 곳 |
| 보내는 것 | 기존 입력 채널(텍스트) `{"type":"phase","err_ms":e}`, e = (0.5 − φ̄) × P ∈ [−P/2, P/2] | 새 채널 없이 |
| 서버 루프 | PI: 보고마다 보정량 += 0.25 · e + 적분(0.05 · Σe); 보정량을 틱마다 **최대 ±1 ms** 씩 다음 틱 마감에 더한다(양수 = 늦춤) | 낮은 이득으로 왕복 흔들림에 둔하게, 적분으로 화면 주기와 60 Hz 의 차(예: 59.94 Hz)를 따라감. 틱당 1 ms 제한으로 프레임 간격이 15.7–17.7 ms 안에 머문다 |
| 안전 장치 | e 가 유한하지 않거나 \|e\| > P/2 + 0.5 ms 면 버림. 2 s 동안 보고가 없으면 보정량·적분을 0 으로(고정 틱으로 돌아감). 적분 크기 제한 ±4 ms | 이상한 보고나 끊긴 클라이언트에 흔들리지 않게 |
| 여러 클라이언트 | 처음 phase 를 보낸 클라이언트만 따른다(그 연결이 끊기면 다음에 보내는 클라이언트) | 서버 렌더 루프가 하나라 틱도 하나다 |
| 스위치 | `serve --phase-lock on|off`(이번 구현의 기본 on — 수용 기준을 못 맞추면 off 로 바꾼다), 클라이언트는 `?phase=0` 이면 보고하지 않음 | A/B 와 되돌리기 |
| 송신 경로 | 클라이언트마다 쓰기 스레드(바로 보냄) + 막힘 읽기. `--send poll` = 이전 경로(A/B 용) | 위 "찾은 원인" — 위상 잠금의 전제(위상이 안정해야 잠글 수 있음) |
| 기록 | 서버 `--log` 에 보고마다 `{"type":"phase","err_ms","applied_ms","integral_ms"}` | 수렴 확인 |

## 단위 시험(구현과 함께)
모의: 서버 틱 60 Hz, 화면 59.94 Hz 와 60 Hz 두 경우, 도착 = 틱 + 10 ms + 흔들림 ±2.5 ms(고정 씨앗 의사난수), 처음 위상은 경계(φ ≈ 0.02 / 0.98) 포함 여러 값. 30 프레임마다 보고. **수렴**: 3,000 프레임 뒤 위상 평균이 0.5 ± 0.1, 경계 ±0.15 안의 도착 < 1 %. **흔들리지 않음**: 수렴 뒤 틱 간격이 15.7–17.7 ms 밖으로 나가지 않고 보정량의 표준편차 < 0.5 ms.

## 측정 계획(측정 전 고정)
- 같은 세션 A/B(C1–C4, measure-env), 세 갈래 번갈아: **poll·끔**(지금 main), **쓰기 스레드·끔**, **쓰기 스레드·켬**(제안 기본) × immediate, orbit 5 회씩 + replay ×60 3 회씩. 시작·끝을 감독에게 알림. 실패·무효는 같은 조건 1 회 재실행·파일 보존.
- **수용 기준(감독)**("off" = 쓰기 스레드·끔과 poll·끔 둘 다에 대해 본다): orbit 빠짐 모든 실행 ≤ 1 %; `input_screen_latency_p50` ≤ off + 2 ms; `event_screen_latency` preview·refined p50 ≤ off + 2 ms; 서버 늦은 틱이 off 보다 나빠지지 않음; replay 빠짐은 보고만.
- 못 맞추면 기본은 off, `--phase-lock on` 은 선택지로만.
- 판정 값(P3.4, server-video.md §2.3)은 그대로 두고 "고친 뒤" 행을 따로 싣는다.

## 대가와 한계
- **여러 클라이언트**: 첫 클라이언트만 맞는다. 나머지는 지금처럼 우연 위상.
- **60 Hz 가 아닌 화면**(144 Hz 등): 서버 60 fps 를 화면 주기에 맞출 수 없다 — 그런 화면에서는 프레임 버퍼(`?pacing=buffer|adaptive`, 결정 0039·0040)가 맞다. 데모 안내에 적는다.
- 틱 간격이 보정 동안 최대 ±1 ms 흔들린다(인코더는 고정 60 fps 시간표를 쓰지만 표시에는 영향 없음).
- 헤드리스 측정의 rAF 는 실제 화면 상태를 따른다(C3 로 60 Hz 확인).
