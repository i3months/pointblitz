# 0040 측정 화면 시계(C3)·화면 기준 지연·적응형 프레임 다듬기

- 상태: 구현·측정 끝, 수용 기준 통과 → 기본값 adaptive, 감독 검토 대기
- 날짜: 2026-10-08
- 결정한 사람: 감독(C3 채택, 판정을 화면 기준으로, 0039 수용 기준), 작업자(재는 방법, 적응형 다듬기 세부)
- 관련: 결정 0038(측정 유효성 C1·C2), 0039(프레임 버퍼), docs/bench/server-video.md §2.1

## 맥락
1. **화면 시계가 측정 중에 바뀐다.** Windows 의 화면 끄기 시간(AC 300 s)이 지나 디스플레이가 꺼지면, Chrome 의 프레임 시계(rAF — 헤드리스·headed 모두)가 60 Hz 에서 약 56.6 Hz(17.7 ms)로 떨어진다. 2026-10-08 13:18:17(마지막 사용자 입력 13:13:17 + 300 s)에 떨어졌고, 화면을 깨운 뒤 같은 실행은 59.93 Hz 로 돌아왔다. 서버 영상은 60 fps 로 보내므로 56.6 Hz 에서는 프레임이 쌓여 buffer 의 지연이 늘었다(PR #37 의 replay +25 ms 가 이것).
2. **입력 → 표시를 "그린 시각" 으로 쟀다.** rAF 밖(디코더 콜백)에서 그린 프레임은 다음 렌더링 갱신 때 화면에 나오고, rAF 안에서 그린 프레임은 그 갱신에 나온다. 그래서 immediate 가 실행마다 평균 4–12 ms 유리했다. SPEC 의 문구는 "화면에 그려질 때" 다.
3. 0039 의 buffer 는 끊김을 없앴지만 지연 비용이 승인 전제보다 커 보였다(1 의 오염 포함). 감독은 P4.6 전에 적응형 다듬기를 필수로 두었다.

| 판정 | 서버 영상의 입력 → 표시와 `event_latency` 는 **screen 기준으로 판정·수용**, 기존(그린 시각) 값은 진단으로 함께 싣는다. P3.4 판정은 바꾸지 않는다 | 감독 결정(입력). `event_latency` 도 같은 문제라 같은 기준으로 맞춘다(작업자 결정, 감독 요청에 따라 측정 전에 기록) |

## 측정 계획(측정 전 고정)
- 같은 세션, keep-display, C1·C2·C3 적용. 실패한 실행만 같은 조건으로 1 회 재시도(실패 파일 보존), C3 무효 실행은 같은 조건으로 1 회 다시 돌린다(무효 파일 보존, 보고에 적음).
- adaptive / buffer / immediate 번갈아 orbit 5 회씩, replay ×60 3 회씩(raw 저장).
- **0039 수용 기준(감독)**: adaptive 가 replay·orbit 모두 `input_screen_latency_p50` ≤ immediate + 16.7 ms 이고 ≤ 40 ms, orbit 빠짐 모든 실행 ≤ 1 %. 못 맞추면 출시 기본값은 immediate, buffer·adaptive 는 선택지로 두고 C(위상 맞추기)를 다시 본다.

## 대가
- **소유자 PC 의 화면을 깨운다 — 측정 동안만.** 실행이 시작될 때 0 거리 마우스 이동 1 회로 꺼진 화면을 켜고, 실행이 끝나면 켜 두기 요청을 푼다(그 뒤에는 Windows 화면 끄기 시간대로). 전원 설정·시스템 설정은 바꾸지 않는다. 소유자가 PC 를 자유롭게 쓰라고 했다.
- 지난 실행 중 raw 가 없는 것은 중앙값만으로 감사해 도중 변화를 놓칠 수 있다.

## P0.6 기준값(감독 결정 — 소유자가 2026-10-08 감독에게 위임)
- P0.6 three.js(cold·orbit·replay ×60, 5 회씩)를 keep-display 로 다시 재서 별도 행으로 싣고, 지난 숫자는 "범위 밖(C3)" 표시와 함께 둔다. 감사: P0.6 14 회 중 11 회가 56.2–58.1 Hz.
- SPEC §7.1 frame_time 목표(2.8/3.8/6.0 ms)는 무효였던 기준 측정에서 나왔으므로, 다시 잰 값으로 바꾸는 것은 "기준 측정 유효성 정정" 이다. **소유자가 2026-10-08 "기준값 변경은 감독이 정해도 됩니다" 라고 감독에게 위임했다.** 감독이 SPEC 변경 PR 로 받고, 이전 값과 판정 이력을 보존한다.
- 그때 native·browser frame_time 판정을 새 기준으로 다시 하고 이전 판정과 함께 싣는다.

## 결과 (2026-10-08 13:38–13:50, docs/bench/server-video.md §2.2)
- 24 회 모두 C1·C2·C3 통과(59.88 Hz), 실패·재실행 0 — keep-display 가 동작했다.
- adaptive: orbit 빠짐 0.40 %(최대 0.66 %, 0/5 > 1 %), 입력 → 표시 p50(screen) orbit 28.1 ms(immediate 25.1, +3.0), replay 33.1 ms(immediate 33.0, +0.1). **수용 기준 통과 → 웹 클라이언트 기본값을 adaptive 로 바꿨다.**
- 대가: refined `event_latency`(screen) 가 immediate 보다 약 40 ms 길다(150 대 108 ms, 목표 250 안). 원인 분리 안 함.
