# 0025 기준 방식의 원판 텍스처에서 밉맵을 끈다

- 상태: 승인
- 날짜: 2026-10-07
- 결정한 사람: 작업자 제안 → 감독 승인(PR #10 검토, 2026-10-07)
- 관련: 결정 0007(원형 2 px, PLY 색 그대로), 0019(기준 방식 세부 — 원판 텍스처 + alphaTest), PR #9 검토 중간

## 맥락
P1.3 에서 PointBlitz 캡처를 기준 방식(three.js) 캡처와 비교하자 두 가지가 드러났다.

1. **색:** 기준 방식의 모든 점이 약 10 % 어둡다(같은 픽셀 예: three.js `[85, 82, 79]` 대 PointBlitz `[94, 92, 89]`). 위치 어긋남은 없다(±1 px 이동 비교에서 0 이동이 가장 가깝다).
2. **모양(감독 발견):** 기준 방식이 칠한 픽셀이 더 많다(overview 15.81 % 대 15.60 %, close_dense 78.06 % 대 72.78 %). PointBlitz 셰이더의 원 판정을 끄면 기준 방식과 같아진다.

원인은 같다. 결정 0019 의 원판 텍스처(`CanvasTexture`)는 기본으로 밉맵을 만든다. 2 px 점에서는 작은 밉 단계가 쓰이고, 거기서 원판과 투명(검정) 모서리가 평균되어
(1) 색이 회색으로 곱해지고 (2) 알파가 모서리까지 0.5 를 넘어 사실상 2×2 사각형이 된다. 결정 0007 의 "원형, PLY 색 그대로" 와 다르다.

## 선택지
| 선택지 | 장점 | 단점 |
|---|---|---|
| ① PointBlitz 를 기준 방식 결과(2×2 사각형)에 맞춘다 (감독 의견) | P0.6 측정을 건드리지 않는다 | 색이 어두워지는 결함까지 따라 하지 않는 한 SSIM 이 낮다. 결정 0007 과 다르다. "three.js 를 제대로 쓰면" 나오는 화면이 아니다 |
| **② 기준 방식의 밉맵을 끈다** | 결정 0007 그대로(원형·PLY 색). 두 구현의 화면이 거의 같아져 화질 비교가 의미 있다 | 기준 방식 코드가 바뀌므로 P0.6 이 유효한지 확인해야 한다 |

## 결정
②. `baseline/three/main.js` 의 원판 텍스처에 `generateMipmaps = false`, `minFilter = magFilter = NearestFilter`.
A/B 확인용으로 `?mipmaps=1`(이전 동작)을 남긴다(`run.mjs --query mipmaps=1`).

## 근거

### 화면 (RTX 4070, event_14, 고정 시점 8곳 — `pointblitz-bench compare`)
| | 밉맵 켬(이전) | 밉맵 끔(이 결정) |
|---|---:|---:|
| SSIM 평균(PointBlitz 대비) | 0.9425 | **0.9919** |
| SSIM 최저 | 0.7671(close_dense) | 0.9828(top_down) |
| 같은 픽셀의 평균 색 차(north) | 15.56 | 1.96 |
| 밝은 픽셀 close_dense (PointBlitz 72.78 %) | 78.06 % | 72.89 % |
| 밝은 픽셀 overview_sw (PointBlitz 15.60 %) | 15.81 % | 15.60 % |

남는 차이는 겹친 점 중 어느 점이 보이느냐(깊이 형식이 다름: three.js 일반 Z 24 bit 대 PointBlitz reversed-Z f32)로 보인다.

### 성능 A/B (같은 세션, 켬·끔을 번갈아 5 회씩, vsync 켬)
| 지표 | 밉맵 켬 중앙값 (범위) | 밉맵 끔 중앙값 (범위) |
|---|---|---|
| cold event_latency | 1,018.2 (973.5–1,049.5) ms | 955.6 (946.7–1,018.8) ms |
| cold 해석 | 712.9 (703.0–725.2) ms | 710.7 (702.8–725.6) ms |
| orbit frame_time_total p50 | 2.9 (2.8–3.0) ms | 2.8 (2.8–3.0) ms |

차이는 실행 간 범위 안이다(p95 는 범위가 겹친다). 텍스처 1 회 샘플의 필터만 바뀌므로 비용 차가 작다는 예상과 맞다.
**P0.6 수치(docs/bench/baseline-three.md)는 그대로 둔다.** 목표 "frame_time ≤ 기준 방식" 에는 더 엄격한 쪽인 P0.6 값(2.8 / 3.8 / 6.0 ms)을 쓴다.

## 대가
- 결정 0019 의 표에 쓴 "원형 2 px" 는 실제로는 밉맵 때문에 2×2 사각형·어두운 색이었다. 0019 에 정정 표시를 붙인다.
- 기준 방식 캡처를 다시 만든다(`target/bench/baseline-three-nomip`).
