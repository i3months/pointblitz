# 0045 서버 영상 120 fps(선택지)

- 상태: **승인**(감독, PR #55 검토 2026-10-08) — 120 fps 는 선택지, 기본 60 fps
- 날짜: 2026-10-08
- 결정한 사람: 소유자(만들고 잰다), 작업자(방법·지표), 감독(측정 전에 정할 다섯 가지 — 아래)
- 관련: 결정 0036(serve), 0040(화면 기준 지연, C3), 0041(C4), 0042(송신 경로·위상 잠금)

## 맥락
- 서버 영상은 60 fps 고정이었다. 소유자 질문: 대역폭을 더 쓰면 빨라지는가. 서버 영상에서 대역폭을 더 쓰는 길은 프레임을 더 자주 보내는 것이다.
- `serve --fps` 는 이미 있었으나 orbit 시나리오가 "프레임마다 1.5°" 라 fps 를 바꾸면 회전 속도가 바뀌었다.
- 스모크(각 1 회, 2026-10-08 19:4x): 120 fps 에서 서버 한 틱 = 그리기 3.7 + 압축 3.5 ms(예산 8.3 ms 안), 늦은 틱 2.8 %, 빈 화면 주기 0.39 %(60 fps 4.87 %), 받은 데이터 약 2 배, 입력 → 화면 p50 20.1 ms(60 fps 16.6 ms — 60 fps 는 위상에 따라 실행마다 크게 흔들려 한 번으로는 판단할 수 없음).

## 결정
| 항목 | 고른 것 | 이유 |
|---|---|---|
| 무엇을 위해 | **이 PC 의 60 Hz 화면에서**: ① 입력 → 화면 지연(서버 틱 대기가 평균 반 틱 = 8.3 → 4.2 ms 줄 수 있음), ② 화면 주기 빈 칸(주기마다 새 프레임이 두 장 오므로 위상과 무관하게 빈 주기가 줄 수 있음). **120 Hz 화면용 효과는 이 PC 에 120 Hz 화면이 없어 재지 못한다**(대가) | 감독 ① |
| 지표 | `input_screen_latency` p50/p95(판정과 같은 화면 기준), `video_frame_missed_pct`(SPEC 정의 그대로: 60 Hz 화면 주기 중 새 프레임이 하나도 그려지지 않은 비율 — 120 fps 에서도 정의가 그대로 성립한다), `event_screen_latency` preview·refined, 서버 늦은 틱, 회전 중 비트레이트(Mbps = 받은 바이트 / 회전 시간) | |
| 유효성 | C1–C4 그대로, C3 는 60 Hz 화면 기준 그대로(감독 ②). **단, C4 의 "서버 늦은 틱 > 1 %" 는 120 fps 갈래에서는 오염 검출이 아니라 그 모드의 결과(예산 8.3 ms 를 못 지킨 비율)이므로 무효 기준으로 쓰지 않고 결과로 보고한다.** 60 fps 갈래는 그대로 적용 | 스모크에서 120 fps 의 늦은 틱 2.8 % 는 오염이 아니라 그리기 + 압축이 예산에 가까워서다 |
| orbit | 시간 기준: 0.5 s 기다린 뒤 12 s 동안 초당 90°(`orbit_plan(fps)`). **60 fps 에서는 기존과 같은 30 / 720 / 1.5°** — 단위 시험 `orbit_plan_keeps_the_60_fps_scenario` 로 고정(감독 ④) | P4.6 판정 값이 바뀌지 않는다 |
| 기본값 | **60 fps 그대로**, 120 fps 는 `serve --fps 120` 선택지(감독 ⑤) | |
| 비트레이트 | 기록하고 비용 모델의 네트워크 표에 120 fps 행을 더한다(감독 ③) | |

## 측정 계획(측정 전 고정)
- 같은 세션 A/B(C1–C4, measure-env), 60 / 120 fps 번갈아(기본 송신 경로, 위상 잠금 끔, pacing immediate), orbit 5 회씩 + replay ×60 3 회씩. 실패·무효(위 예외 외)는 같은 조건 1 회 재실행·파일 보존. 시작·끝을 감독에게 알림.
- 보충(감독, 측정 시작 뒤·결과를 보기 전에 기록): 120 갈래에서도 **C4 의 CPU 보정은 그대로 무효 기준**이다(늦은 틱만 예외 — 스크립트는 늦은 틱이 유일한 사유일 때만 받아들인다). 120 갈래의 늦은 틱 비율은 실행별로 보고하고 수용 판정 표에도 함께 싣는다(기준 항목은 아님).
- 보고: 위 지표의 실행별 값과 중앙값. 판정 값(P4.6, 60 fps)은 바꾸지 않는다.
- **"120 fps 가 나은가" 의 기준(측정 전)**: 120 fps 가 orbit 입력 → 화면 p50 을 60 fps 보다 낮추고(중앙값 비교), 빈 화면 주기가 모든 실행 ≤ 1 % 이면 "60 Hz 화면에서도 이득" 으로 적는다. 아니면 "60 Hz 화면에서는 이득 없음(120 Hz 화면은 미측정)" 으로 적는다. 어느 쪽이든 기본값은 바꾸지 않는다 — 기본을 바꾸려면 따로 기준을 세운다.

## 대가
- 데이터가 약 2 배(회전 중 약 150 Mbps 예상), 서버 GPU 를 약 2 배 쓴다(사용자 한 명당).
- 120 Hz 화면에서의 효과(움직임이 부드러워지는 것)는 이 PC 에서 재지 못한다.
- 서버 한 틱이 예산(8.3 ms)에 가까워, 더 큰 장면·해상도에서는 늦은 틱이 늘 수 있다.

## 결과 (2026-10-08 19:32–19:40, 같은 세션, 16 회 모두 C1–C4 유효, 다시 돌린 실행 0)
| 지표(중앙값, 괄호는 실행별) | 60 fps | 120 fps |
|---|---|---|
| orbit 입력 → 화면 p50 (screen) | 22.5 ms (22.5, 16.5, 33.1, 33.7, 18.9) | **16.4 ms** (14.4, 16.5, 13.6, 18.5, 16.4) |
| orbit 입력 → 화면 p95 | 30.4 ms | 30.1 ms |
| orbit 빈 화면 주기 | 0.79 % (최대 1.85 %, 1/5 > 1 %) | **0.26 %** (최대 0.39 %, 0/5 > 1 %) |
| orbit 서버 늦은 틱 | 0 % (모든 실행) | 2.79 % (2.91, 2.79, 2.78, 1.71, 2.84) |
| orbit 서버 틱: 그리기 / 압축 p50 | 5.73 / 5.56 ms | 3.78 / 3.47 ms |
| orbit 받은 데이터 (회전 12 s 중심) | 113.0 MB(약 75 Mbps) | 215.1 MB(약 143 Mbps) |
| replay ×60 입력 → 화면 p50 | 33.1 ms | 23.2 ms |
| replay ×60 미리보기 / 정밀 반영 p50 (screen) | 20.5 / 82.8 ms | 22.7 / **114.1 ms** |
| replay ×60 빈 화면 주기(보고만) | 1.80 % | 1.47 % |
| replay ×60 서버 늦은 틱 | 0.10 % | **7.84 %** (8.04, 7.77, 7.84) |
| replay ×60 받은 데이터 | 10.3 MB | 10.4 MB |

- **미리 정한 기준 통과 → "60 Hz 화면에서도 이득"**: orbit 입력 → 화면 p50 이 22.5 → 16.4 ms(−6.1 ms)로 낮아졌고, 빈 화면 주기는 모든 실행 ≤ 1 %(최대 0.39 %)였다. 60 fps 는 위상에 따라 실행마다 16.5–33.7 ms 로 흔들렸는데 120 fps 는 13.6–18.5 ms 로 좁다 — 화면 주기마다 새 프레임이 두 장 오므로 위상의 운이 작아진다.
- **대가(결과에서 확인)**: ① 회전 중 데이터 약 2 배(75 → 143 Mbps). ② replay 에서 서버 늦은 틱 7.8 %, 정밀 반영 82.8 → 114.1 ms(+31 ms) — 스냅샷을 서버 GPU 에 올리는 틱이 8.3 ms 예산을 넘는다. ③ 서버 GPU 를 사용자 한 명당 약 2 배 쓴다. ④ p95 는 그대로(30 ms).
- 120 fps 에서 틱당 그리기·압축이 60 fps 보다 짧았다(3.8 / 3.5 대 5.7 / 5.6 ms) — 쉬지 않고 일해 GPU 클럭이 높게 유지된 것으로 본다(P4.4 와 같은 현상, 확인은 안 함).
- 기본값은 60 fps 그대로(감독 ⑤). 회전 반응이 중요하고 대역폭·서버 GPU 여유가 있으면 `serve --fps 120` 을 쓴다. 기본을 바꾸려면 replay 의 늦은 틱·정밀 반영 지연을 포함한 기준을 따로 세운다.
