# 0050 지연을 줄이는 구조 변경 — 영상 서버의 로컬 읽기, 변환을 스냅샷이 나올 때 한 번

- 상태: 승인(소유자 결정 2026-10-09, 감독 검토 PR #73)
- 날짜: 2026-10-09
- 결정한 사람: 소유자(두 변경을 한다), 감독(범위·측정), 작업자(방법)
- 관련: 0026(청크 전달, 요청마다 변환), 0036(서버 영상), 0049(측정 규칙), [comparison-incremental.md](../bench/comparison-incremental.md)

## 맥락(감독 진단, 2026-10-09)
- web(WebGPU) replay ×60, 정밀 스냅샷 14(40 MB 청크): 서버 파일 읽기 18–21 ms(요청마다 디스크에서), 브라우저의 마지막 청크 도착 108–160 ms, GPU 올리기 ≤ 1 ms, 그 뒤 표시까지 20–30 ms. 서버 total 75–160 ms 는 브라우저의 마지막 청크 시각과 거의 같다.
- 같은 서버의 `/static` 40 MB 파일을 Chrome 이 받는 데만 41–99 ms(서버 변환 없음) — 브라우저 수신이 바닥이다. 그리기(1–2 ms)는 병목이 아니다.
- 소유자: 대역폭은 제약이 아니다(대역폭을 늘려 속도를 얻는 선택은 괜찮고, 비용으로 적지 않는다).
- 서버 영상은 영상 서버가 재생 서버의 `/chunks` 를 HTTP 로 받아(같은 장비여도) 서버 GPU 에 올린다 — 받기·변환이 그대로 지연에 들어간다.

## 결정
### ① 영상 서버가 같은 장비의 데이터를 직접 읽는다
- `pointblitz-server serve --data <dir>`: 알림은 지금처럼 재생 서버의 `/events` 로 받고, 스냅샷은 `<dir>/<file>` 의 PLY 를 **직접 읽어 같은 프로세스에서 청크로 바꿔** 장면에 넣는다(HTTP·소켓 복사 없음). 변환은 재생 서버와 같은 코드(`pointblitz-io` 로 옮김)와 같은 판단(미리보기 차분 = 앞 스냅샷 뒤에 덧붙인 레코드만)을 쓴다.
- 차분 판단에 필요한 "앞 스냅샷에 덧붙였는가" 는 재생 서버가 시작할 때 바이트로 확인한 값(0026)을 `/manifest.json` 의 `appends` 로 알려 준다(새 필드, 기존 클라이언트는 무시).
- `--data` 가 없으면 지금처럼 HTTP(`/chunks`)로 받는다 — 데이터가 다른 장비에 있을 때.

### ② 변환을 스냅샷이 나올 때 한 번 해 두고 `/chunks` 를 메모리에서 보낸다
- 재생 서버는 스냅샷 알림을 보내는 **그 순간 변환을 시작**하고(다른 스레드), 결과(전체 전달 청크, 그리고 앞 스냅샷에 덧붙인 경우 그 차분 청크)를 메모리에 둔다. `/chunks/<seq>?have=` 요청은 같은 `chunks::plan` 으로 고른 결과를 메모리에서 바로 보낸다. 변환이 아직 끝나지 않았으면 끝나는 대로(만들어지는 청크부터) 보낸다.
- 알림은 늦추지 않는다(변환을 끝내고 알리지 않는다). **그래서 변환 시간은 지금처럼 측정 구간(알림 → 화면) 안에 남는다** — 0026 의 원칙("변환은 클라이언트의 측정 구간 안, 기준 방식의 해석과 같은 자리")을 지킨다. 바뀌는 것은 요청마다 디스크에서 다시 읽고 바꾸던 일이 알림 때 한 번으로 줄고, 요청이 오기 전에 변환이 먼저 시작된다는 것이다.
- 알림 없이 들어온 요청(cold: 클라이언트가 늦게 붙어 이미 나온 스냅샷을 받음)은 처음 한 번 변환해 메모리에 둔다. 운영 서버라면 파일이 생길 때 이미 바꿔 두었을 스냅샷이다.
- **메모리**: 점당 16 B 에 청크 머리 80 B. 정밀 스냅샷 14(250만 점) 전체 전달이 약 40 MB, 차분은 0.3–0.9 MB. 최근 스냅샷 2 개분(지금 것과 그 앞 것: 차분 판단과 늦게 받는 클라이언트용)만 두고 그보다 오래된 것은 버린다 — 재생 서버의 추가 메모리는 최대 약 80 MB. 버린 스냅샷을 다시 요청하면 그때 변환한다.
- **0026 과의 관계**: 0026 은 "요청 때 변환" 을 골랐다(이유: 변환 비용이 측정 구간 안에 들어간다). 0050 은 시점을 "알림 때" 로 바꾸되 측정 구간 안에 두는 점은 같다. 0026 의 "서버 시작 때 미리" 선택지(변환이 측정 밖)는 여전히 고르지 않는다.

### 이번 범위가 아닌 것
- ③ 거친 것 먼저 보내기, ④ 좌표 16 비트 — SPEC 변경이라 이번에는 하지 않는다(소유자가 고르지 않음).

### 측정(0049 규칙 그대로, 측정 전 고정)
- 같은 세션 번갈아, **변경 전(main 0404a79) 대 변경 후**: web · webgl · native · video 의 replay ×60 10 회 + cold 10 회, C1–C4, 부트스트랩 95 % 구간(씨앗 48049). 비 = 변경 전 ÷ 변경 후(1 보다 크면 빨라짐), 구간이 1 을 포함하면 "차이 없음".
  - 변경 전·후를 한 세션에서 번갈아 돌리기 위해 두 빌드(재생 서버·영상 서버·web 모듈)를 나란히 두고 대상마다 고른다.
- 단계 분해: 정밀 스냅샷마다 서버의 읽기·변환·전송 시각과 브라우저의 `fetch_start → headers → last_chunk_received → uploaded → presented`(web 의 원시 마크), video 는 서버 쪽의 같은 단계.
- 그리기·화질이 바뀌지 않았음을 고정 시점 8 곳 SSIM 으로 확인(변경 전 대 변경 후, native·web·video).

## 대가
- 재생 서버 메모리 최대 약 80 MB 더. 영상 서버는 `--data` 일 때 PLY 를 직접 읽으므로 데이터 디렉터리에 접근할 수 있어야 한다.

## 다시 볼 조건
- 변환을 알림 전에 끝내는 운영 구성(파일이 생길 때 변환하고 다 되면 알림)을 쓰게 되면, 측정 구간을 "파일이 생긴 시각 → 화면" 으로 바꿔 다시 잰다.
