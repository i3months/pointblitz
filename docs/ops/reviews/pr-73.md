# PR #73 검토 노트 — 결정 0050(지연 구조 변경), TASKS P4.9–P4.11, 감독 진단 기록

## 확인한 것

- 범위가 소유자 결정과 같다: ① 영상 서버의 같은 장비 데이터 직접 읽기(`serve --data`), ② 재생 서버의 한 번 변환·메모리 전달. ③ 거친 것 먼저·④ 좌표 16 비트는 SPEC 변경이라 빠져 있다.
- 맥락의 수치가 감독 진단 원 기록(`pb-wt-diag/target/diag/lat`)과 같다: 서버 읽기 18–21 ms, 마지막 청크 108–160 ms, 업로드 ≤ 1 ms, 표시 +20–30 ms, `/static` 40 MB 41–99 ms.
- §8 의 두 진단이 감독 원 기록(d1–d4, w1)과 같다.
- 측정 계획이 0049 규칙(같은 세션 번갈아, C1–C4, 10 회, 부트스트랩 95 %, 씨앗 48049)을 그대로 쓰고, 측정 전에 고정돼 있다. 변경 전 커밋(0404a79)이 정해져 있다.
- 대역폭을 대가로 적지 않았다(소유자 지시).
- CI 세 작업 모두 통과.

## 작업자가 짚은 선택 — 알림을 늦추지 않음(동의)

- ② 에서 변환을 "알림 때 시작, 알림은 늦추지 않음" 으로 했다. 변환을 끝내고 알리면 변환 시간이 측정 구간(알림 → 화면) 밖으로 빠져, 클라이언트에서 해석하는 기준 방식(B0·B2)보다 유리해진다. 0026 의 원칙을 지키는 선택이다.
- 운영 관점에서도 손해가 아니다: 파일이 생긴 시각 → 화면 으로 보면 변환은 어느 쪽이든 그 안에 있고, 알림을 먼저 보내면 변환과 전송이 겹쳐 오히려 빠를 수 있다. 다시 볼 조건에 "파일이 생긴 시각 → 화면" 재측정이 적혀 있다.
- 그래서 ② 의 이득은 요청마다의 디스크 읽기 제거와 변환이 요청 전에 시작되는 몫으로 작을 수 있다. 큰 이득은 ①(영상 서버가 HTTP 로 40 MB 를 받지 않음)에서 기대한다. 결과는 측정으로 판정한다.
