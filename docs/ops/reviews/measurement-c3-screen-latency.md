# 측정 유효성 C3(화면 주기)와 입력 → 표시의 "화면" 시각 — 감독 결정(소유자 위임)

- 날짜: 2026-10-08
- 결정한 사람: 감독(소유자 위임, 측정 정의). SPEC 의 목표 수치는 바꾸지 않는다.
- 계기: 작업자 보고 — 헤드리스 Chrome 의 rAF("측정 속 화면") 속도가 13:18 무렵 60.0 Hz → 56.5–57.5 Hz 로 떨어졌다(모니터는 60 Hz 그대로, 헤드리스는 소프트웨어 타이머). 감독이 자기 기록으로 확인했다:

| 감독 실행 | 시각 | rAF |
|---|---|---|
| PR #33 재현 orbit 2 회 | 11:48–11:50 | 60.00 / 59.93 Hz(간격 p50 16.70 ms) |
| PR #37 재현 replay ×60 buffer·immediate | 13:24–13:28 | **약 56.8 Hz(간격 p50 17.6 ms)** |

56.6 Hz 로 그리는데 서버가 60 fps 로 보내면 클라이언트 큐가 늘 차서 buffer 의 지연이 +2 주기 가까이 된다. PR #37 의 replay +25 ms, orbit 5 번째 쌍 41 ms, 그리고 **감독의 PR #37 재현 값(p50 45.1, p95 54.3)은 이 상태에서 잰 것**이다.

## 결정

### (a) 오염 기준 C3 — 채택
- **C3: 실행의 rAF 속도(측정 구간의 화면 주기 수 ÷ 시간)가 59.5–60.5 Hz 밖이면 그 실행은 무효(오염).** C1·C2(결정 0038)와 같이 판정에서 빼고, 숫자와 함께 남기고, 같은 조건으로 다시 잰다.
- 브라우저를 쓰는 모든 대상(three.js, browser WebGPU·WebGL2, server video)에 똑같이 적용한다. native 는 창의 실제 표시 주기(present 간격)로 같은 범위를 본다.
- **지난 판정에도 감사(audit)한다**: P0.6·P1.5·P2.5·P3.4·P4.1~P4.3 의 판정·진단 실행 중 raw(rAF 시각)가 남아 있는 것을 C3 로 확인한다. 범위 밖 실행이 판정에 쓰였으면 그 판정 행에 표시하고, 같은 조건으로 다시 재서 별도 행으로 싣는다. 지난 문서의 숫자는 지우지 않는다.

### (b) 입력 → 표시는 "화면에 나온 때" 로 — 채택(기존 값도 함께)
- SPEC §7.1 의 정의는 "입력 번호가 돌아온 영상 프레임이 **화면에** 그려질 때까지" 다. 기존 값(캔버스에 그린 때)은 immediate(rAF 밖에서 그림 → 다음 렌더링 갱신 때 화면에 나옴)에 평균 약 8 ms 유리했다. 그래서 **판정과 0039 수용 기준은 `input_screen_latency`(그 프레임이 화면에 나오는 렌더링 갱신 시각)로 한다.** 기존 `input_latency` 는 진단값으로 함께 싣는다.
- `event_latency` 의 `presented` 도 같은 문제가 있으면(rAF 밖에서 그리는 구현) 같은 기준으로 맞출지를 측정 전에 정해 결정 기록에 적는다.
- **P3.4 판정은 바꾸지 않는다.** 새 정의는 immediate 쪽에 몇 ms 를 더할 뿐이라 여유가 큰 P3.4 의 통과가 뒤집히지 않는다. 다시 잴 때 새 정의 값을 별도 행으로 싣는다.
- `input_screen_latency` 를 재는 방법(어떤 시각을 "화면에 나온 때" 로 보는가)은 PR 에서 감독이 검토한다.

### (c) 적응형(`?pacing=adaptive`) A/B — C3 를 지키며 다시
- 0039 의 수용 기준(PR #37 검토)은 그대로 쓰되, 입력 → 표시는 `input_screen_latency` 로 판단한다. C3 를 통과한 실행만 쓴다.
- 헤드리스의 화면 주기가 56.6 Hz 로 계속 떨어지면 headed Chrome(실제 60 Hz 모니터)을 시험해도 된다. 다만 **측정 환경을 바꾸는 것이므로 모든 브라우저 대상에 같이 적용**하고 결정 기록을 쓴다.

## 정정

- PR #37 검토의 조건 ⑤ 판단 근거("실제 비용이 +8 ms 전제의 2~3 배", replay p50 여유 4.9 ms)는 **C3 오염 실행에서 나온 값**이다. 60 Hz 였던 orbit 1~4 쌍의 buffer 입력 → 표시 p50 은 33.3 / 33.3 / 33.3 / 40.8 ms 다. 화면 기준으로 보면 orbit 의 실제 차이는 약 +8 ms 로 처음 전제와 맞는다(작업자 보고, 다음 PR 에서 확인).
- 0039 의 조건부 승인과 수용 기준은 유지한다. 판단은 C3 를 지킨 새 A/B 로 다시 한다.
