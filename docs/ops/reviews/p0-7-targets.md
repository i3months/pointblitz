# P0.7 목표 수치 — 감독 결정(소유자 위임)

- 날짜: 2026-10-07
- 결정한 사람: 감독. 소유자가 2026-10-07 소유자 결정을 감독에게 넘겼고, 작업자가 소유자에게 올린 제안에는 P1.2 가 끝날 때까지 답이 없었다.
  소유자가 다른 값을 정하면 그 값이 우선한다(SPEC §9 에 새 변경 기록).
- 근거 데이터: [docs/bench/baseline-three.md](../../bench/baseline-three.md)(P0.6, three.js 기준 방식)
- 원칙: PointBlitz 를 재기 **전에** 정한다. 측정 결과에 맞춰 바꾸지 않는다(SPEC §8.1). 대역폭은 목표에 넣지 않는다(INTENT 원칙 2, 바이트는 기록만).

## 측정 조건(모든 목표에 공통)

`flight-01`, 이 PC(RTX 4070 12 GB, i7-13700F, Windows 11), 루프백 서버, 1920×1080, vsync 켬(결정 0021), 측정 방법은 결정 0020.
`replay` 는 ×60 을 목표 판정에 쓰고 ×1 도 같은 목표로 따로 보고한다(×1 이상치는 P1.5 전에 재확인 — PR #7 검토).

- `first_frame` 은 탐색·모듈 로드가 섞여 흔들리므로 보고만 한다(목표 없음).
- `frame_time` 비교는 두 구현의 점 모양이 같을 때만 유효하다(PR #9 검토 중간 — P1.3 전에 결정).
- 서버 영상(P3)의 `event_latency`(인코딩 포함 화면 반영)와 입력 → 화면 지연 목표는 P3 착수 때 정한다.
- 저사양 GPU 는 목표 대상이 아니라 비용 모델(결정 0011)로 추정해 보고한다.

## 왜 이 값인가

- preview 는 새 점만 보낸다(2~5만 점 × 16 B ≈ 0.3~0.9 MB, 결정 0009). 해석이 없으므로(결정 0008) 50 ms 는 기준 방식의 약 1/9 이고 여유가 있다.
- refined 는 전체(최대 40 MB 청크)를 받는다. 기준 방식 루프백 67.6 MB 다운로드가 88~124 ms 였으므로 40 MB 수신 + 업로드로 200 ms 는 달성 가능하다. 해석 711 ms 를 없애는 효과가 드러나는 값이다.
- 메인 스레드 블록 0 회는 "해석을 메인 스레드에서 하지 않는다" 는 설계 주장(README)을 검증 가능한 숫자로 바꾼 것이다.
- `mem_cpu` 300 MB: 렌더러 기본 약 45 MB(P0.5 memtest) + 청크 40 MB × 2(세대 교체) + wasm·여유. 기준 방식의 약 1/3.
- 그리기는 이 GPU 에서 기준 방식이 이미 빠르므로 "나빠지지 않는다" 를 목표로 한다.
