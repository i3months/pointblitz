## 판단: "캡처로 확인" 을 CPU 투영 검사로 대신한 것

**받아들인다.** 이유:
- 완료 기준의 목적은 "8곳 모두 점이 화면에 들어온다" 다. 렌더러가 없는 지금 확인할 수 있는 가장 직접적인 방법이 투영 검사이고,
  감독이 다른 구현·다른 규약(three.js `lookAt`)으로 다시 투영·래스터해 같은 결과와 눈으로 확인 가능한 영상을 얻었다.
  축·위 방향·시야각 해석 오류가 있었다면 여기서 드러났을 것이다.
- 실제 GPU 캡처는 P0.4 의 `orbit` 시나리오(8곳 캡처 저장)와 P1.3 에서 한다. TASKS 의 P0.2 완료 표시에 이 대체를, P0.4 완료 기준에 8곳 캡처 재확인을 적었다.

## 기록만 (중간·낮음)

| 수준 | 내용 |
|---|---|
| 중간 | 넓은 시점 7곳은 화면 픽셀의 7~18 % 만 점이 찍힌다(감독 래스터 기준, 격자 덮임 10~23 %). 경계 구를 세로 시야에 맞춘 결과라 의도대로이지만, 프레임 시간 비교에서 "화면을 꽤 채우는 중간 거리" 경우가 close_dense 하나뿐이다. P0.6 측정 결과를 보고 필요하면 0.5 d 시점을 추가하는 새 결정 기록을 쓴다. |
| 낮음 | `parse_header` 는 `end_header\n` 만 찾는다. `ply\r` 은 받아들이면서 `end_header\r\n` 헤더는 영원히 `Incomplete` 가 된다. 둘 중 하나로 맞춘다(P1.1). |
| 낮음 | `vertex_count * stride` 는 `checked_mul` 로 바꾼다(악의적 헤더, wasm32 의 32 bit usize). |
| 낮음 | 색 속성이 u8 이 아니면(예: float) 조용히 흰색이 된다. 에러나 경고로 구분한다(P1.1). |
| 낮음 | 증분 입력에서 `parse_header` 를 재시도할 때마다 버퍼 전체를 처음부터 훑는다. P1.1 증분 파서에서 이어서 찾게 한다. |
| 낮음 | 시점 JSON 의 `source` 문자열을 이스케이프하지 않는다(파일 이름에 `"` 가 있으면 깨진다). |
