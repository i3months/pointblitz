## 판단 1 — `mem_cpu` 미달: 목표를 바꾸지 않고, 백엔드도 바꾸지 않는다

- 목표는 PointBlitz 를 재기 전에 정했다. 결과를 보고 고치지 않는다(SPEC §8.1). **판정은 "미달" 로 남긴다.**
- DX12 로 바꾸면 293 MB 로 들어오지만, 프레임 시간·preview 지연이 나빠진다. 목표 하나를 맞추려고 실행 환경을 고르는 것은 측정에 맞춘 조정이다. 작업자 판단에 동의한다.
- 감독이 덧붙여 기록한다: native 의 `mem_cpu` 는 프로세스 전체(GPU 드라이버 사용자 모드 메모리 포함)다. three.js 의 값은 렌더러 프로세스만이고 드라이버는 GPU 프로세스에 있다. 즉 정의가 비대칭이다.
  **이 비대칭은 목표를 정할 때(감독, P0.7) 놓친 것이다.** 지금 정의를 고치면 사후 기준 변경이 되므로 고치지 않는다. 대신 다음을 한다.
  - native.md 에 이 비대칭과 "데이터 전 74~102 MB · 첫 프레임 직후 약 236 MB" 분해를 진단값으로 싣는다(이미 있음).
  - P2(browser)의 `mem_cpu` 는 SPEC 대로 렌더러 프로세스로 판정한다. 그때 GPU 프로세스 값도 함께 싣는다.
  - native 메모리를 줄이는 시도(스테이징 버퍼 해제 시점, 교체 중 이전 세대 해제 순서 등)는 목표를 바꾸지 않는 개선으로, 하게 되면 결정 기록과 함께 한다.

## 판단 2 — PR #7 미해결(P0.6 ×1 느림)을 닫는다

**받아들인다.** 이번 세션(P1.5b)의 three.js ×1 은 455.1 / 606.6 ms 로 ×60 과 같은 수준이다. 30 분 앞 세션(P1.5a)의 ×60 은 반대로 약 2 배 느렸다. 그러니 ×1 이라서가 아니라 세션 흔들림으로 보는 것이 맞다.
감독은 자기 작업이 P1.5a 와 겹쳤는지 파일 시각으로 확인했다. 감독의 PR #12 검토(빌드·GPU 실행)는 00:01:39 에 끝났고, P1.5a 는 00:01:58~00:06:24 다. 2 배 느렸던 replay ×60(00:04~00:06) 동안 감독은 git 작업만 했다.
→ 감독 작업으로는 설명되지 않는다. 원인은 여전히 미확인이며, "구현 간 비교는 같은 세션 번갈아 측정값으로만" 이라는 native.md 의 원칙이 이 문제의 대응이다.
