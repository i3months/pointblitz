## 판정 해석 (작업자가 물은 세 가지)

1. **프레임 빠짐을 실행 중앙값으로 판정한 것 — 받아들인다. 단 꼬리를 판정 옆에 적는다.**
   - 실행 중앙값은 이 프로젝트의 모든 판정이 써 온 집계 규칙(`aggregate.mjs`)이다. 측정 뒤에 집계 규칙을 바꾸면 사후 기준이 된다. 판정은 **통과(중앙값)** 그대로 둔다.
   - 그러나 PR 5 회 + 감독 2 회 = **7 회 중 2 회가 1 % 를 넘었다**(4.86 %, 1.85 %). replay ×60 의 빠짐도 1.5~5.1 % 다(보고만). 서버 늦은 틱은 낮다 — 작업자 분석대로 클라이언트 쪽(디코딩 출력과 화면 주기의 맞물림)이 원인으로 보인다.
   - **해야 할 것**:
     - server-video.md 판정 행에 "7 회 중 2 회 > 1 %(감독 재현 포함)" 를 적는다.
     - 공개 비교표(P4)에는 중앙값과 함께 실행별 최대(또는 전체 주기를 합친 비율)를 싣는다.
     - 클라이언트 쪽 빠짐 원인 분리를 P4 전 진단 작업에 넣는다.
2. **응답 없는 입력 1 개**(replay·cold, 감독 실행에서도 1 개씩) — 서버 종료 때 오가던 마지막 입력으로 보는 설명을 받아들인다. orbit 은 0. 측정 끝 처리(마지막 입력 뒤 한 주기 기다림)로 0 이 되게 하면 깔끔하다(낮음).
3. **three.js 프레임 시간이 이번 세션에 크게 짧은 것(p99 6.0 → 2.1 ms)** — 감독 재현에서도 같다(2.10~2.14). 목표는 SPEC 대로 P0.6 고정값으로 판정한다. 그래서 browser `frame_time` 미달(P2.5) 판정은 바뀌지 않는다. 같은 세션 비교표에서는 이번 세션 값을 그대로 싣는다. 원인 미상은 P4 전 frame 진단(PR #21 검토)에서 함께 본다.
