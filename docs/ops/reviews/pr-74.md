- 대상 커밋: `231ec23`
- 결과: **통과**

## 확인한 것

- 범위가 결정 0050 과 같다: 재생 서버는 알림 때 변환을 시작하고(알림은 늦추지 않음) 최근 스냅샷 2 개분을 메모리에 두고 `/chunks` 를 메모리에서 보낸다. 영상 서버는 `--data` 일 때 PLY 를 직접 읽어 같은 프로세스에서 변환한다. `--data` 가 없으면 HTTP 경로 그대로.
- 변환 코드는 `pointblitz-io::convert` 한 곳에 모였고, 재생 서버와 영상 서버가 같은 `plan` 을 쓴다. 기존 공개 API 는 바뀌지 않았다.
- 시험(감독 재실행): `cargo test -p pointblitz-io -p pointblitz-bench` 모두 통과(22 + 26 + 1). 그중 "알림 때 변환 결과 = 요청 때 변환 결과(바이트)", "세 번째 스냅샷이 가장 오래된 것을 밀어냄" 확인. CI 세 작업 통과.
- 감독 스모크(판정 아님, replay ×60, 번갈아 2 회씩, 화면 기준 p50):

| 영상 서버 | 미리보기 | 정밀 |
|---|---|---|
| HTTP(지금 경로) | 13.1 · 28.4 ms | 129.6 · 82.2 ms |
| `--data`(로컬 읽기) | 16.3 · 20.5 ms | 49.9 · 55.5 ms |

  작업자 스모크(정밀 125.9 → 63.6 ms)와 같은 방향이다. 판정은 P4.11 측정으로 한다.

## 기록만

| 수준 | 내용 |
|---|---|
| 낮음 | `Conversion::chunk` 는 요청마다 청크(최대 4 MB)를 복사한다. 메모리 대역 안에서 수 ms 이하로 보이며, P4.11 의 단계 분해에서 서버 전송 몫이 크면 `Arc<[u8]>` 공유로 바꿀 후보. |
| 낮음 | 영상 서버의 `--data` 는 알림 시각부터 변환을 시작하므로 재생 서버와 같은 측정 구간이다. `Delivered` 의 `headers_at` 자리에 변환 시작 시각이 들어간다 — 단계 분해 문서에 이 뜻을 적을 것. |
