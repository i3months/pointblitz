# PR #41 검토 노트 — 제안: 서버 틱을 클라이언트 화면 위상에 맞추기(C)

- 대상 커밋: `440daf4`
- 결과: **통과(문서) + 감독 결정: C 를 한다**

## 결정 (감독, 소유자 위임)

**C 를 한다.** 이유:
- 기본 pacing(immediate)의 orbit 프레임 빠짐이 C1~C4 측정에서 5/5 회 > 1 %(감독 재현 7.79 %)다. SPEC §7.1 서버 영상 목표 미달이다.
- 버퍼(B·adaptive)는 끊김을 없애지만 지연 수용 기준을 못 맞췄다(결정 0040·0041).
- C 는 지연을 늘리지 않고 도착 위상을 화면 갱신 경계에서 떼어 낸다. P4.3 근거와 맞는다: 위상이 가운데였던 실행은 0.13~0.26 %.
- **목표를 맞추려 정의를 바꾸는 것이 아니라**, 사용자가 보는 끊김을 고치는 제품 개선이다. 판정 값(P3.4, §2.3)은 그대로 두고 "고친 뒤" 행을 따로 싣는다.

## 조건(제안서 보강)

1. 구현 **전에** 결정 기록을 쓴다. 루프 이득·한 틱 최대 보정·안전 장치(위상 메시지 없음·이상값 무시), `serve --no-phase-lock`, 측정 계획을 적는다.
2. 단위 시험: 모의 도착 시각(고정 위상 + 흔들림 ±2.5 ms, 화면 59.94 Hz 같은 주기 차)으로 루프가 수렴하고 흔들리지 않음을 보인다.
3. 같은 세션 A/B(C1~C4, `gpu-watch`, 시작·끝 알림): phase-lock 켬/끔 × immediate, orbit 5 회·replay ×60 3 회 이상.
4. **수용 기준**:
   - orbit 빠짐 **모든 실행 ≤ 1 %**
   - `input_screen_latency` p50 ≤ 끔 + 2 ms
   - `event_screen_latency` preview·refined p50 ≤ 끔 + 2 ms
   - 서버 늦은 틱 비율이 끔보다 나빠지지 않을 것
   - replay 빠짐은 보고만
5. 기준을 못 맞추면 기본은 끔으로 두고 옵션으로만 남긴다.
6. 한계(여러 클라이언트, 60 Hz 가 아닌 화면)는 결정 기록 대가 절에 적는다. 그런 화면에서는 B(버퍼)가 맞다는 안내를 데모·문서에 남긴다.
