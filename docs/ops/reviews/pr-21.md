## 판단

1. **SPEC §7.1 판정을 받아들인다.**
   - WebGPU 두 모듈: preview·refined·cold·main_thread_block 통과, `frame_time` 셋 다 미달.
   - WebGL2: main_thread_block 미달(시작 1 회), `frame_time` 미달, 나머지 통과.
   - native(새 메모리 방법): 지연·frame 통과, 메모리는 기록만(소유자 결정 PR #20).
   목표를 고치지 않았고 미달을 미달로 보고했다. 판정 전에 고치지 않았다(PR #18 검토대로).
2. **브라우저 `frame_time` 미달의 해석은 아직 가설이다.** 0033 이 적었듯, WebGPU 의 동기화 프레임은 1 픽셀 복사 + `mapAsync`(비동기 왕복)로 GPU 완료를 기다린다. three.js 는 동기 `readPixels` 로 기다린다. **동기화 방법이 달라** 측정값에 그리기 비용과 동기화 비용이 섞인다. native 1.55 ms 와 같은 core 라는 점은 동기화 비용 쪽을 시사하지만, 증명되지 않았다.
   - 판정은 목표·정의대로 **미달** 로 둔다. PointBlitz 에 불리한 쪽이라 공정성 위험은 없다.
   - 다만 **공개 비교표(P4)에 쓰기 전에** 동기화와 무관한 진단을 한다. 예: 두 구현 모두 N 프레임을 연속 제출하고 마지막에 한 번만 동기화해 프레임당 평균을 낸다. 또는 WebGPU 타임스탬프 쿼리. 결과에 따라 "그리기가 느리다" 인지 "완료를 아는 비용이 크다" 인지 구분해 적는다.
   - browser.md §3 의 원인 설명에 "가설" 이라는 표시를 붙인다(다음 문서 갱신 때).
3. **0033 승인** — 메모리 폭증 원인을 좁힌 실험(그리기만 132 MB / 완료 대기만 143 MB / 둘 다 1,666 MB)이 근거로 충분하다. 화면 밖 + 1 픽셀 readback 은 native `orbit` 과 같은 구조다.
4. **0034 승인** — "메모리를 위해 속도를 내주지 않는다" 원칙을 적었고, A/B 에서 차이가 범위 안·방향 엇갈림이라 바꾸지 않는다. 0027 은 본문을 두고 대체 표시만 했다.
5. 작업자가 측정 중 메인 작업 폴더에서 `git stash` 를 한 번 했다고 보고했다(0033 초안만, 바로 복구). 감독 쪽 worktree·측정에는 영향이 없었다. 공유 폴더에서 stash 같은 전역 조작은 피한다.
