## 판단

1. **쓰기 스레드 송신을 기본으로 둔 것을 받아들인다 — 결함 수정이다.**
   - 이전 송신 경로는 클라이언트 스레드가 1 ms 읽기 제한으로 소켓을 읽고 그 사이에 보냈다. Windows 소켓 읽기 제한은 시스템 타이머 틱(15.625 ms) 단위로 끝나므로, 프레임이 15.6 ms 격자로 나갔다(받은 시각 톱니: 프레임마다 −1.1 ms, 13 프레임마다 +15 ms).
   - P4.3 에서 본 "도착 흔들림·위상 운" 의 실체이고, 판정 전 목표 맞추기가 아니라 VUI 수정(0037)처럼 의도와 다른 동작을 고친 것이다. 이전 경로(`--send poll`)를 A/B 용으로 남긴 것도 좋다.
   - 이로써 P3.4·P4.3 의 server video 측정은 이 결함을 안고 잰 값이다. 판정 이력은 그대로 두고, P4.6 전체 비교가 새 기본(쓰기 스레드)으로 다시 판정한다.
2. **위상 잠금: 수용 기준 미달 → 기본 끔(선택지).** 빠짐 최대 1.05 %(수렴 중 처음 42 주기)와, 지연 증가(input +10 ms, refined +11~+52 ms > +2 ms)가 걸린다. 규칙대로다.
3. **위상 잠금 다듬기를 1 회만 더 허용한다.** 감독이 본 원인 후보는 이렇다.
   - **목표 위상**: 지금은 도착을 주기 가운데(φ ≈ 0.5)로 맞춘다. immediate 그리기는 다음 rAF 에 화면에 나가므로 도착 → 화면 대기가 반 주기(약 8 ms)로 고정되어 입력 지연이 는다. **rAF 직후(φ ≈ 0.2 안팎)를 목표로 하면** 대기는 약 3~4 ms 로 줄고, 경계까지의 여유(±3 ms 이상)도 도착 흔들림(±2.4 ms, 쓰기 스레드)보다 크다.
   - **refined 증가**: 스냅샷 교체 때 서버 프레임이 늦는 틱에 잠금이 반응해 틱을 미루는지 서버 로그로 가른다.
   - **수렴 속도**: 처음 수렴을 빠르게(작은 변경) 한다.
   - 같은 수용 기준(PR #41 검토)으로 C1~C4 A/B 를 한 번 더 한다. **이번에도 못 맞추면 위상 잠금은 끔으로 확정하고 더 다듬지 않는다**(PROJECT §3 의 반복 반려 원칙 취지). 그 경우 P4.6 은 쓰기·끔 기본으로 재고, 서버 영상 프레임 빠짐의 SPEC 판정은 실측 그대로(실행별 분포 포함) 보고한다.
