# 서버 영상: 서버 틱을 클라이언트 화면 위상에 맞추기(C) — 제품 개선 제안

- 날짜: 2026-10-08
- 상태: 제안(감독이 정함). 결정 0039 의 감독 조건 ⑤ — adaptive 가 C1–C4 재측정에서 수용 기준을 못 맞춰(replay 입력 → 표시 45.1 > 40 ms) 기본값이 immediate 로 돌아갔고, C 를 다시 본다.
- 근거: docs/bench/diagnostics.md P4.3, docs/bench/server-video.md §2.3, docs/notes/frame-pacing-proposal.md

## 문제(다시)
- 프레임은 사라지지 않는다. 서버 틱(60 Hz 타이머)과 브라우저 화면 갱신(60 Hz vsync)의 위상이 연결 때 우연히 정해지고, 프레임 도착이 화면 갱신 경계 근처에 걸리면 "빈 주기 + 두 장 주기" 가 생긴다.
- C1–C4 를 지킨 세션에서 immediate 는 orbit 빠짐 8.15 %(5/5 > 1 %) — SPEC 미달. 버퍼(B, adaptive)는 끊김을 없애지만 지연을 더한다(+6.5–11.3 ms, replay 에서 수용 기준 넘음).

## 제안: 클라이언트가 위상 오차를 알려 주고, 서버가 틱 시각을 천천히 옮긴다
| 항목 | 내용 |
|---|---|
| 클라이언트가 재는 것 | 프레임마다 "디코딩이 끝난 시각" 이 화면 갱신 주기(rAF 시각 격자) 안의 어디인지 = 위상 φ ∈ [0, 1). 0.5 초마다 최근 30 프레임의 위상 중앙값 |
| 목표 위상 | rAF 밖에서 그린 프레임은 다음 렌더링 갱신에 나간다. 갱신 경계에서 가장 먼 곳 = φ ≈ 0.5(주기 가운데)에 도착하게 한다. 도착 흔들림(p5–p95 약 ±2.5 ms, P4.3)이 경계를 넘지 않는 여유가 생긴다 |
| 보내는 것 | 기존 입력 채널(텍스트)로 `{"type":"phase","err_ms":…}` — err = (0.5 − φ) × 주기, −8.3 … +8.3 ms |
| 서버가 하는 것 | 다음 틱 마감 시각에 err 의 일부(예: ×0.25, 한 틱에 최대 ±1 ms)를 더한다 — 위상 고정 루프. 주기 자체(60 Hz)는 그대로 두되, 화면 시계가 60.0 이 아니면(예: 59.94) 같은 루프가 천천히 따라간다 |
| 지연 | 늘지 않는다. 오히려 φ ≈ 0.5 면 도착 → 화면 대기가 평균 반 주기로 고정된다(지금은 0–1 주기 사이에서 연결마다 우연) |
| 여러 클라이언트 | 서버는 렌더 루프가 하나라 틱도 하나다. 첫 클라이언트(또는 입력을 보내는 클라이언트)를 따르고, 나머지는 지금처럼 우연 위상. 클라이언트별 틱은 렌더를 나눠야 해 범위 밖 |
| 안전 | 위상 메시지가 없거나 이상하면(|err| > 주기의 절반, 연속 큰 점프) 무시하고 지금처럼 고정 틱. `serve --no-phase-lock` 으로 끔(A/B) |

## 예상 효과와 위험
- 빠짐: 경계에서 멀어지므로 도착 흔들림 ±2.5 ms 로는 빈 주기가 거의 생기지 않는다(P4.3: 위상이 가운데였던 실행은 0.13–0.26 %). 서버가 늦는 틱(스냅샷 교체 때)은 그대로 남는다.
- 위험: (1) 서버→클라이언트 왕복의 흔들림으로 루프가 흔들릴 수 있다 — 낮은 이득과 한 틱 최대 1 ms 로 막는다. (2) 헤드리스 측정의 rAF 시계와 실제 화면이 다를 수 있다(C3 로 60 Hz 를 확인하는 이유). (3) 주사율이 60 이 아닌 화면(144 Hz)은 서버 60 fps 와 맞출 수 없다 — 그때는 B(버퍼)가 맞다. 화면 주사율을 클라이언트가 함께 알려 주면 서버가 정할 수 있다(이번 범위 밖).
