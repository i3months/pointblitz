# skyrecon 이 "덧붙임" 정보를 내도록 할지 (기록)

- 날짜: 2026-10-08
- 상태: 제안만. skyrecon 은 다른 팀원의 저장소다. 바꾸려면 소유자·팀과 따로 정한다.
- 관련: 결정 0026, docs/bench/native.md §3, PR #12 검토

## 왜 필요한가
PointBlitz 는 preview 스냅샷이 앞 스냅샷을 비트 단위로 그대로 품고 점만 덧붙였을 때, 새 점만 보낸다(preview 전송 4.1~65.5 MB → 0.35~0.87 MB).
이를 알려면 지금은 서버가 두 파일을 바이트로 비교해야 한다. 요청마다 하면 43 ms 가 들어, preview 목표(≤ 50 ms)를 거의 다 쓴다.
벤치 서버는 시작 때 한 번 비교해 메타데이터처럼 쓰지만, 실제 서비스에서는 스냅샷이 실시간으로 생기므로 그렇게 할 수 없다.

## 제안
skyrecon 이 스냅샷을 쓸 때 다음 중 하나를 함께 낸다.

| 방법 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. 옆 파일(JSON) | `event_13_…ply.json`: `{"appends_to": 12, "base_points": 2404412}` | PLY 를 건드리지 않는다 | 파일이 하나 늘어난다 |
| B. PLY 주석 | 헤더에 `comment pointblitz appends_to 12 base_points 2404412` | 한 파일 | PLY 를 읽는 다른 도구에는 무해하지만 헤더 형식에 기대게 된다 |
| C. 이벤트 메시지 | 스냅샷 알림(지금의 SSE)에 같은 필드 | 이미 있는 경로 | 파일만 보는 도구는 모른다 |

작업자 의견은 A(가장 덜 침습적이고 검증이 쉽다). 서버는 이 정보를 믿되, 점 수(`base_points`)가 맞지 않으면 전체 전달로 바꾼다(지금의 `plan` 과 같은 안전장치).

## 정해야 하는 것
- skyrecon 쪽에 이 출력을 넣을지, 넣는다면 어느 방법인지 — 소유자·skyrecon 담당과 결정.
