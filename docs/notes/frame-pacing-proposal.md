# 서버 영상 프레임 고르게 하기 — 제품 개선 제안

- 날짜: 2026-10-08
- 상태: **감독 결정 — 선택지 B(클라이언트 한 프레임 버퍼)**(PR #35 검토, 2026-10-08). 이전 상태: 제안. 판정용이 아니다: 하게 되면 P3.4 판정 값은 그대로 두고, 고친 뒤 값을 별도 행으로 싣는다.
- 근거: [docs/bench/diagnostics.md](../bench/diagnostics.md) P4.3

## 문제
서버 영상은 프레임을 잃지 않지만(주기당 1.00 장), 서버 틱과 브라우저 화면 vsync 의 위상이 경계 근처에 걸린 연결에서는 "한 주기에 두 장, 옆 주기는 빈 화면" 이 자주 생긴다.
9 회 중 4 회가 1 % 를 넘었고 최대 15.23 % 였다. 사용자에게는 회전 중 미세한 끊김으로 보인다.

## 선택지

| 선택지 | 하는 일 | 입력 → 표시 지연 | 끊김 | 구현 |
|---|---|---|---|---|
| A. 그대로 | — | p50 18–21 ms | 위상에 따라 0.1–15 % | 없음 |
| **B. 한 프레임 버퍼(클라이언트)** | 디코딩한 프레임을 바로 그리지 않고 쌓아 두고, rAF 마다 한 장씩 그린다(쌓인 게 2 장을 넘으면 오래된 것을 버림) | 평균 약 +8 ms(0–16.7 ms), 예상 p50 26–29 ms(목표 ≤ 50) | 위상과 무관하게 거의 0(디코딩이 한 주기 넘게 밀릴 때만) | `web/video.js` 수십 줄 |
| C. 위상 맞추기(서버) | 클라이언트가 자기 vsync 위상과 도착 시각을 서버에 알리고, 서버가 틱 시각을 옮겨 프레임이 vsync 주기 한가운데 오게 함 | 늘지 않음 | 크게 줄지만 흔들림이 크면 남음 | 서버 틱 조정 + 시계 차 추정, 클라이언트마다 한 틱이라 여러 클라이언트면 절충 |
| D. B + C | C 로 맞추고 B 는 안전망 | +0–8 ms | 거의 0 | B + C |

## 제안
**B 를 먼저** 한다. 이유: 구현이 작고 클라이언트만 바뀌며(서버·전송 형식 그대로), 끊김을 위상과 무관하게 없애고, 지연 증가(약 +8 ms)가 목표(≤ 50 ms) 안에 넉넉히 들어간다.
C 는 B 의 지연이 문제가 될 때(예: 원격 서버에서 네트워크 지연이 더해질 때) 다시 본다.

## 하게 되면
- 결정 기록(지연과 매끄러움의 맞바꿈, 측정 전후).
- `web/video.js` 에 `?pacing=buffer|immediate`(기본은 결정에 따름), 같은 세션 A/B(orbit 5 회씩, gpu-watch).
- 보고: 빠짐 실행별 분포, 입력 → 표시 p50/p95, `event_latency` — P3.4 판정 행은 그대로 두고 "고친 뒤" 행을 따로.
