# 공개 전 진단 (P4.1–P4.4)

판정·목표는 바꾸지 않는다. 판정은 결정 0020(프레임마다 동기화)으로 한 값 그대로다. 여기서는 그 숫자의 원인을 측정으로 가른다.

## P4.1 browser `frame_time` — 동기화 방법과 무관하게

**질문**: browser 의 `frame_time_total`(P2.5 미달)이 그리기 비용인가, 브라우저에서 "GPU 가 끝났다" 를 아는 비용인가.

**방법**: orbit 의 동기화 프레임을 `batch=N` 으로 — N 프레임을 연달아 제출하고 한 번만 동기화해 프레임당 평균을 낸다(동기화 비용이 N 프레임에 나뉜다).
네 구현 모두 같은 방법(three.js `?batch=`, web `?batch=`, native `--batch`), N = 1(판정 방법) 과 30, 번갈아 3 회씩. 2026-10-08, 이 PC(RTX 4070, Chrome 155), 같은 세션.

| 구현 | N = 1 p50 / p95 / p99 | N = 30 p50 / p95 / p99 | CPU 호출(N = 30) p50 |
|---|---|---|---:|
| three.js | 1.70 / 1.90 / 2.10 | 1.60 / 1.73 / 1.81 | 0.01 |
| native | 1.49 / 1.74 / 1.93 | 1.37 / 1.41 / 1.45 | 0.08 |
| **browser WebGPU** | 3.10 / 4.20 / 4.74 | **1.43 / 1.57 / 1.63** | 0.04 |
| browser WebGL2 | 3.50 / 6.00 / 13.12 | 3.92 / 4.96 / 6.70 | 3.92 |

단위 ms. 재현: `node baseline/three/run.mjs … --scenario orbit --query batch=30 --label …`, `node bench/native/run.mjs … --scenario orbit --batch 30`.

**결과**
- **WebGPU**: 동기화를 나누면 프레임당 1.43 ms 로 native(1.37)와 같고 three.js(1.60)보다 짧다. P2.5 의 3.1 / 4.2 / 4.7 ms 는 **그리기가 아니라 동기화(1 픽셀 복사 + `mapAsync` 왕복)** 비용이다. browser.md §3 의 가설을 확인했다.
- **WebGL2**: 프레임 시간이 CPU 호출 시간과 같다(3.5~3.9 ms). 비용은 GPU 가 아니라 **`render_offscreen` 호출 안**(wgpu GL 백엔드가 명령을 CPU 에서 GL 호출로 옮기는 부분)에 있다. 동기화를 나누면 p99 꼬리가 13.1 → 6.7 ms 로 줄지만 없어지지 않는다 → 나머지 꼬리도 CPU 쪽(P4.2 에서 더 가름).
- three.js·native 는 동기화 몫이 0.1~0.5 ms 로 작다.

**판정에 미치는 영향**: 없다. SPEC §7.1 판정은 결정 0020 의 프레임마다 동기화로 한다(browser 미달 그대로). 공개표(P4.6)에는 두 값을 함께 싣고, 차이가 동기화 방법에서 온다는 것을 각주로 적는다.

## P4.2 WebGL2 `frame_time` 꼬리 (p95·p99 13~14 ms)

**질문**: WebGL2 의 프레임 비용(P4.1: 총시간 = CPU 호출 시간)과 p99 꼬리는 어느 단계에서 생기나.

**방법**: `Viewer.render_offscreen` 안의 단계 시각(`performance.now`)을 프레임마다 남김 — record(렌더 패스·버퍼 쓰기 기록), copy(1 픽셀 읽기 복사 기록), finish, submit. orbit `?stages=1`.
이어서 1 픽셀 읽기 복사를 끄는 A/B(`?glcopy=0`), 번갈아 3 회씩, `bench/gpu-watch.mjs` 로 GPU 기록(오염 0). 11:29~11:31 의 첫 A/B 는 감독 재현과 겹쳐 버렸다.

| 단계 (WebGL2, 960 프레임) | p50 | p95 | p99 | 최대 |
|---|---:|---:|---:|---:|
| record | 0.00 | 0.10 | 0.10 | 0.20 |
| copy | 0.00 | 0.00 | 0.10 | 0.10 |
| finish | 0.00 | 0.10 | 0.20 | 0.50 |
| **submit** | **4.30** | **6.90** | **8.60** | 13.80 |

가장 느린 1 % 프레임(평균 11.5 ms)은 거의 전부 submit(11.4 ms)이었다. WebGPU 는 모든 단계가 0.2 ms 이하(GPU 일은 비동기).

| WebGL2 orbit, 같은 세션 3 회씩 | `frame_time_total` p50 / p95 / p99 | submit p50 / p99 |
|---|---|---|
| 읽기 복사 켬(기본) | **4.2 / 6.6 / 13.4** ms | 3.90 / 10.20 ms |
| 읽기 복사 끔 | 6.2 / 10.9 / 11.5 ms | 0.10 / 0.30 ms |

**결과**
- WebGL2 에서는 wgpu GL 백엔드가 **submit 때 GL 호출을 실제로 내보내고**, Chrome 의 명령 버퍼 → ANGLE → D3D11 을 거쳐 실행된다. 프레임 비용과 꼬리는 이 실행 경로에 있다. 우리 쪽 기록(record)·동기화는 원인이 아니다.
- 읽기 복사를 끄면 submit 은 0.1 ms 가 되지만, 같은 일이 페이지의 `readPixels` 동기화 때로 옮겨 가 프레임이 오히려 느려졌다(p50 4.2 → 6.2 ms). 복사는 비용이 아니라 GL 일이 흘러가는 시점을 정한다 → **기본값(켬)을 유지**하고 `?glcopy=0` 은 진단용으로만 남겼다.
- p99 13 ms 꼬리는 세 실행 중 두 실행에서 나타났다(6.5 / 13.4 / 13.6 ms) — Chrome GL 경로 안의 흔들림으로 보인다. 줄이려면 그리기를 Worker(OffscreenCanvas)로 옮기거나 WebGPU 를 쓰는 길밖에 없다(WebGPU 는 P4.1 에서 native 와 같음).

**판정에 미치는 영향**: 없다(미달 그대로). 공개표에는 WebGL2 를 "대체 경로" 로 표시하고 이 원인을 각주로 단다.

## P4.3 server video 클라이언트 쪽 프레임 빠짐

**질문**: orbit 프레임 빠짐이 실행마다 0.1~12 % 로 흔들리고(P3.4: 7 회 중 2 회 > 1 %), 서버 늦은 틱은 낮다. 프레임이 사라지는가, 다른 원인인가.

**방법**: 브라우저 클라이언트가 프레임마다 (서버 틱 시각, 받은 시각, 그린 시각)을, 화면 주기(rAF)마다 그린 프레임 수를 남긴다(`web/video.js`, `bench/video/frame-drops.mjs`). server video orbit 을 5 회 + A/B 8 회, `bench/gpu-watch.mjs`(오염 0), 측정 전후를 감독에게 알림.

**결과 1 — 프레임은 사라지지 않는다**: 13 회 모두 그린 프레임 수 = 화면 주기 수(주기당 1.00). 빈 주기 수 ≈ 두 장 그린 주기 수(예: 53 대 53, 97 대 93). 즉 "빠짐" 은 한 주기에 두 장이 몰리고 옆 주기가 비는 것이다.

**결과 2 — 원인은 서버 틱과 화면 vsync 의 위상**: 서버 틱 간격은 p5–p95 16.3–17.1 ms 로 고르고, 받는 간격은 14.5–19.1 ms 로 퍼진다. 그린 시각이 vsync 주기 안 어디에 떨어지는지(0 = 주기 시작) 보면:

| 실행(낮은 순) | 빠짐 | 그리기 위상 평균 | vsync 경계 ±15 % 안의 그리기 |
|---|---:|---:|---:|
| 가장 낮은 4 회 | 0.13–0.26 % | 0.42–0.70 | 0.0–10.6 % |
| 중간 | 0.92–3.56 % | 0.03–0.84 | 31.7–67.2 % |
| 가장 높은 3 회 | 6.96–12.71 % | 0.84–0.98 | 59.6–64.6 % |

두 60 Hz 시계(서버 타이머, 브라우저 화면)의 위상 차는 연결할 때마다 우연히 정해진다. 그리기가 주기 한가운데 오면 흔들림이 있어도 같은 주기에 남고, 경계 근처에 오면 흔들림이 프레임을 옆 주기로 밀어 "빈 주기 + 두 장 주기" 가 생긴다.

**기각한 가설 — 서버 송신 경로**: 클라이언트별 스레드가 1 ms 읽기 제한과 송신을 번갈아 하던 것을 쓰기 전용 스레드(채널에 들어오는 즉시 송신)로 바꾼 A/B(4 회씩): 받는 간격 퍼짐·빠짐(legacy 12.7/0.3/3.6/0.1 % 대 thread 10.4/0.9/2.6/0.1 %)이 같았다. 효과가 없어 되돌렸다.

**공개표 지표(P4.6)**: 판정은 SPEC 정의(빈 주기 비율, 실행 중앙값) 그대로 두고, 함께 싣는다 — 실행별 최대, **주기당 그린 프레임 수(1.00)**, 그리고 이 값이 위상에 따라 정해진다는 각주.

**고칠 수 있는 길(후보, 지금은 하지 않음)**: (1) 클라이언트가 한 프레임을 쌓아 두고 rAF 마다 한 장씩 그림 — 빈 주기가 거의 없어지지만 입력→표시가 평균 반 프레임(약 8 ms) 늘어남. (2) 클라이언트가 vsync 위상을 서버에 알려 서버가 틱 위상을 옮김 — 지연을 늘리지 않지만 구현이 큼. 지연과 매끄러움의 맞바꿈이라 정할 때 결정 기록을 쓴다.

## P4.4 three.js `frame_time` 의 세션 간 차이

**질문**: 같은 코드·Chrome·드라이버인데 three.js 의 orbit `frame_time` 이 P0.6·P2.5(2.7–2.8 / 3.6–3.8 / 6.0 ms)와 P3.4·P4.1(1.70 / 1.90 / 2.10 ms)로 갈렸다. native 는 1.5 ms 근처로 같았다.

**찾은 것**
- **빨라진 정도가 비례다**: 시점별 p50 이 P2.5 → P3.4 에서 2.8 → 1.7 ms(0.61 배), close_dense 2.1 → 1.4 ms(0.67 배), overview_sw 3.1 → 1.9 ms(0.61 배). 동기화 같은 고정 비용이 바뀌었다면 모든 시점이 같은 만큼 줄었을 것이다. 비례로 줄었으므로 **GPU 가 Chrome 의 일을 더 빨리 처리한 것**(클럭·전원 상태)으로 본다.
- **세션 시각이 갈린다**: 느린 세션(P0.6, P1.5b, P2.5)은 모두 00:26–02:33, 빠른 세션(P3.4, P4.1, 이번)은 10:52 이후였다. 데스크톱의 다른 GPU 사용 프로그램(Chrome·Discord 등)은 10:10 무렵부터 떠 있었다.
- **이번 세션(빠름, 2026-10-08 11:5x)의 GPU 클럭**(`bench/gpu-watch.mjs`, 3 회씩): three.js orbit 중 중앙 2,490–2,775 MHz(P8/P3 ↔ P0 오감, GPU 사용률 평균 23–35 %), native orbit 중 중앙 2,775 MHz(사용률 33–45 %). three.js 1.70 / 2.00 / 2.20 ms, native 1.48 / 1.73 / 1.88 ms.
- 시스템 타이머 해상도는 지금 1.0 ms 다(Windows 10 2004 이후 요청은 프로세스별이라 다른 앱의 영향은 제한적).

**결론(원인 확인 안 됨)**: three.js 는 프레임마다 `readPixels` 로 GPU 를 기다려 일이 띄엄띄엄 들어오므로, 드라이버의 전원 관리(적응형 클럭)가 클럭을 덜 올렸을 가능성이 크다. 다른 GPU 프로그램이 함께 돌 때는 클럭이 높게 유지된다. native 는 쉬지 않고 제출해 늘 높은 클럭이었다. 밤 세션의 클럭 기록이 없어 확인하지 못했다. GPU 클럭 고정(관리자 권한·시스템 설정 변경)은 하지 않는다.

**재현 조건과 대응**
- 지금부터 모든 측정은 `gpu-watch` 로 클럭을 남긴다(결정 0038). 느린 값이 다시 나오면 클럭으로 바로 확인한다.
- 판정은 SPEC 대로 P0.6 고정값(2.8 / 3.8 / 6.0 ms)이다. 공개표에는 같은 세션 값과 함께 세션 간 차이(three.js 만 크게 흔들림)와 이 해석을 각주로 싣는다.
