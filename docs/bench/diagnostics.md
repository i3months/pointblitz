# 공개 전 진단 (P4.1–P4.4)

판정·목표는 바꾸지 않는다. 판정은 결정 0020(프레임마다 동기화)으로 한 값 그대로다. 여기서는 그 숫자의 원인을 측정으로 가른다.

## P4.1 browser `frame_time` — 동기화 방법과 무관하게

**질문**: browser 의 `frame_time_total`(P2.5 미달)이 그리기 비용인가, 브라우저에서 "GPU 가 끝났다" 를 아는 비용인가.

**방법**: orbit 의 동기화 프레임을 `batch=N` 으로 — N 프레임을 연달아 제출하고 한 번만 동기화해 프레임당 평균을 낸다(동기화 비용이 N 프레임에 나뉜다).
네 구현 모두 같은 방법(three.js `?batch=`, web `?batch=`, native `--batch`), N = 1(판정 방법) 과 30, 번갈아 3 회씩. 2026-10-08, 이 PC(RTX 4070, Chrome 155), 같은 세션.

| 구현 | N = 1 p50 / p95 / p99 | N = 30 p50 / p95 / p99 | CPU 호출(N = 30) p50 |
|---|---|---|---:|
| three.js | 1.70 / 1.90 / 2.10 | 1.60 / 1.73 / 1.81 | 0.01 |
| native | 1.49 / 1.74 / 1.93 | 1.37 / 1.41 / 1.45 | 0.08 |
| **browser WebGPU** | 3.10 / 4.20 / 4.74 | **1.43 / 1.57 / 1.63** | 0.04 |
| browser WebGL2 | 3.50 / 6.00 / 13.12 | 3.92 / 4.96 / 6.70 | 3.92 |

단위 ms. 재현: `node baseline/three/run.mjs … --scenario orbit --query batch=30 --label …`, `node bench/native/run.mjs … --scenario orbit --batch 30`.

**결과**
- **WebGPU**: 동기화를 나누면 프레임당 1.43 ms 로 native(1.37)와 같고 three.js(1.60)보다 짧다. P2.5 의 3.1 / 4.2 / 4.7 ms 는 **그리기가 아니라 동기화(1 픽셀 복사 + `mapAsync` 왕복)** 비용이다. browser.md §3 의 가설을 확인했다.
- **WebGL2**: 프레임 시간이 CPU 호출 시간과 같다(3.5~3.9 ms). 비용은 GPU 가 아니라 **`render_offscreen` 호출 안**(wgpu GL 백엔드가 명령을 CPU 에서 GL 호출로 옮기는 부분)에 있다. 동기화를 나누면 p99 꼬리가 13.1 → 6.7 ms 로 줄지만 없어지지 않는다 → 나머지 꼬리도 CPU 쪽(P4.2 에서 더 가름).
- three.js·native 는 동기화 몫이 0.1~0.5 ms 로 작다.

**판정에 미치는 영향**: 없다. SPEC §7.1 판정은 결정 0020 의 프레임마다 동기화로 한다(browser 미달 그대로). 공개표(P4.6)에는 두 값을 함께 싣고, 차이가 동기화 방법에서 온다는 것을 각주로 적는다.

## P4.2 WebGL2 `frame_time` 꼬리 (p95·p99 13~14 ms)

**질문**: WebGL2 의 프레임 비용(P4.1: 총시간 = CPU 호출 시간)과 p99 꼬리는 어느 단계에서 생기나.

**방법**: `Viewer.render_offscreen` 안의 단계 시각(`performance.now`)을 프레임마다 남김 — record(렌더 패스·버퍼 쓰기 기록), copy(1 픽셀 읽기 복사 기록), finish, submit. orbit `?stages=1`.
이어서 1 픽셀 읽기 복사를 끄는 A/B(`?glcopy=0`), 번갈아 3 회씩, `bench/gpu-watch.mjs` 로 GPU 기록(오염 0). 11:29~11:31 의 첫 A/B 는 감독 재현과 겹쳐 버렸다.

| 단계 (WebGL2, 960 프레임) | p50 | p95 | p99 | 최대 |
|---|---:|---:|---:|---:|
| record | 0.00 | 0.10 | 0.10 | 0.20 |
| copy | 0.00 | 0.00 | 0.10 | 0.10 |
| finish | 0.00 | 0.10 | 0.20 | 0.50 |
| **submit** | **4.30** | **6.90** | **8.60** | 13.80 |

가장 느린 1 % 프레임(평균 11.5 ms)은 거의 전부 submit(11.4 ms)이었다. WebGPU 는 모든 단계가 0.2 ms 이하(GPU 일은 비동기).

| WebGL2 orbit, 같은 세션 3 회씩 | `frame_time_total` p50 / p95 / p99 | submit p50 / p99 |
|---|---|---|
| 읽기 복사 켬(기본) | **4.2 / 6.6 / 13.4** ms | 3.90 / 10.20 ms |
| 읽기 복사 끔 | 6.2 / 10.9 / 11.5 ms | 0.10 / 0.30 ms |

**결과**
- WebGL2 에서는 wgpu GL 백엔드가 **submit 때 GL 호출을 실제로 내보내고**, Chrome 의 명령 버퍼 → ANGLE → D3D11 을 거쳐 실행된다. 프레임 비용과 꼬리는 이 실행 경로에 있다. 우리 쪽 기록(record)·동기화는 원인이 아니다.
- 읽기 복사를 끄면 submit 은 0.1 ms 가 되지만, 같은 일이 페이지의 `readPixels` 동기화 때로 옮겨 가 프레임이 오히려 느려졌다(p50 4.2 → 6.2 ms). 복사는 비용이 아니라 GL 일이 흘러가는 시점을 정한다 → **기본값(켬)을 유지**하고 `?glcopy=0` 은 진단용으로만 남겼다.
- p99 13 ms 꼬리는 세 실행 중 두 실행에서 나타났다(6.5 / 13.4 / 13.6 ms) — Chrome GL 경로 안의 흔들림으로 보인다. 줄이려면 그리기를 Worker(OffscreenCanvas)로 옮기거나 WebGPU 를 쓰는 길밖에 없다(WebGPU 는 P4.1 에서 native 와 같음).

**판정에 미치는 영향**: 없다(미달 그대로). 공개표에는 WebGL2 를 "대체 경로" 로 표시하고 이 원인을 각주로 단다.
