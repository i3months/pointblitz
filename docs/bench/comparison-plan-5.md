# 측정 계획 5 — 청크 v2 · 거친 것 먼저 전후(P4.14, 측정 전 고정)

- 날짜: 2026-10-09. [결정 0051](../decisions/0051-fewer-bytes-coarse-first.md), 판정 규칙은 결정 0049 §3, 방법은 [계획 4](comparison-plan-4.md)와 같다. 바꾸려면 측정 전에 이 문서를 고친다.

## 대상·회수
- **변경 전** = 0050 뒤 main(ff05817: 청크 v1 f32, 전체 전달 파일 순서, 첫 반영 없음), **변경 후** = PR #78 병합 뒤 main(청크 v2-12, 전체 전달 거친 것 먼저).
- `bench/ab.sh` 로 같은 세션 번갈아: web(WebGPU) · webgl · native · video × cold 10 · replay ×60 10, 회차마다 전/후 순서를 뒤집음. 영상 서버는 두 쪽 모두 `--data`(0050 ①, 둘 다 같은 경로 — 차이는 청크만, `VIDEO_DATA=both`).
- 받기 바닥(40 MB 정적 파일)을 시작·끝에 5 회씩.

## 지표와 판정
- **완전 반영**(`event_latency`, 지금까지와 같은 정의): 재생 미리보기·정밀 p50, cold — 비 = 전 ÷ 후, 부트스트랩 10,000 번(씨앗 48049) 95 % 구간, 1 을 포함하면 "차이 없음".
- **첫 반영**(`event_first_latency`, SPEC §6.2): 재생 정밀 p50, cold. 변경 전에는 첫 반영이 따로 없으므로 완전 반영과 같은 값이다(정의대로). 같은 방법으로 비를 낸다.
- **목표 판정**(SPEC §7.1, 변경 후 값, 측정 전 고정): web(WebGPU) 정밀 첫 반영 p50 ≤ 50 ms, video 정밀 첫 반영 p50 ≤ 50 ms(화면 기준 `event_first_screen_latency`). 판정은 변경 후 10 회의 중앙값.
- 기록: 받은 바이트, 메인 스레드 멈춤, mem_cpu.

## 단계 분해(판정 아님) — 감독 노트(PR #77)
- **web 과 webgl 을 나란히**: 정밀 스냅샷마다 `snapshot_received → headers → first_chunk → first_pass_uploaded → first_presented → last_chunk_received → uploaded → presented`(두 대상 모두 원시 마크를 남긴다). P4.11 에서 같은 바이트인데 web 정밀만 "차이 없음"(0.92), webgl 은 1.18 배였던 것을 흔들림인지 이 표로 본다.
- **video 서버 쪽**: 서버 로그의 `received`(알림 받음) → `chunk first_pass`(첫 패스 청크 도착) → `chunk last`(마지막 청크) → 그 틱의 프레임. 영상 서버가 첫 패스에서 새 세대로 바꾸는지, 같은 틱에 끝까지 들어오는지 확인(감독 노트 PR #78).
- **native mem_cpu**: P4.11 의 356 → 376 MB 를 이번 값과 함께 보고, 원인을 한 줄로 적는다(원시 기록의 청크 수·세대 교체 시점으로).

## 그림 확인
- 변경 전 대 변경 후, 고정 시점 8 곳 SSIM: web 과 video. v2-12 와 ③ 순서 때문에 1.0000 이 아니다 — [chunk-v2-choice.md](chunk-v2-choice.md) 의 원인 나누기와 같은 크기(평균 약 0.996)인지, 차이 픽셀이 점 경계 1 px 안(팽창 안 ≥ 99.9 %)인지 본다.

## 목표를 못 지키면
- 결정 0051 "다시 볼 조건" 과 감독 노트(PR #78)대로: 먼저 첫 패스를 앞당기는 서버 쪽 변경(파일을 나눠 읽기, 첫 패스만 먼저 모아 인코딩), 그다음 v2-8(기준은 그 전에 정함). 결과가 불리해도 그대로 싣는다.
