- **송신 경로가 끊김의 큰 원인이었다.** 이전 경로는 Windows 소켓 읽기 제한(시스템 타이머 15.6 ms 단위)을 기다렸다 보내 프레임이 15.6 ms 격자로 나갔다. 쓰기 스레드로 바로 보내면 orbit 빠짐 중앙값 8.14 → 0.79 %, 입력 → 표시도 줄었다. 하지만 서버(60 Hz)와 화면(약 59.94 Hz)의 작은 속도 차로 위상이 실행 중에 흘러 경계에 닿는 실행은 여전히 빠짐이 크다(7.09 % 실행: 위상 0.74 → 0.04 로 흐름).
- **위상 잠금은 그 흐름을 막는다**: 수렴 뒤에는 빈 주기가 거의 없다. 1.05 % 실행의 빈 주기 8 개는 모두 처음 42 주기(위상 0.85 → 0.5 로 끌어오는 동안)였고, 그 뒤 약 720 주기 동안 0 개였다.
- **수용 기준(감독) 판정: 미달** — orbit 빠짐 1/5 실행이 1.05 %(> 1 %), refined `event_latency` p50 이 쓰기 스레드·끔보다 replay +11.3 ms·orbit 의 cold 부분 +38.5 ms(기준 +2 ms). 입력 → 표시·preview·늦은 틱은 통과. refined 는 실행 간 범위가 넓어(100–212 ms) 이 회수로는 차이를 가르기 어렵지만, 기준은 기준이다.
- **그래서 위상 잠금은 기본 끔**(`serve --phase-lock on` 은 선택지). **쓰기 스레드 송신은 기본**으로 둔다 — 수용 기준의 대상이 아니었고 모든 지표에서 이전 경로보다 낫다(감독 확인 요청).
- SPEC 판정(서버 영상 빠짐 ≤ 1 %, 실행 중앙값)으로 보면 새 기본(쓰기 스레드·끔)은 0.79 % 로 통과지만, 5 회 중 2 회가 1 % 를 넘는다(위상 흐름). P4.6 전체 비교에서 실행별 분포와 함께 다시 판정한다.

### 2.5 위상 잠금 다듬기 1 회 뒤(결정 0042) — 마지막 A/B, C1–C4 준수

같은 세션(2026-10-08 15:22–15:30), 두 갈래 번갈아 orbit 5 회씩 + replay ×60 3 회씩. 16 회 모두 C1–C4 통과, 실패·재실행 0. 다듬은 것: 목표 위상 0.65, 오차를 감싸지 않음, 첫 보고 10 프레임, 처음 3 보고 이득 0.75, 교체 프레임·느린 디코딩은 위상 평균에서 뺌.

- 미달 실행(1.05 %)의 빈 주기 8 개는 모두 처음 40 주기(위상 0.97 에서 끌어오는 동안)에 있었다. 그중 0–3 주기의 빈 주기는 거의 모든 실행·모든 갈래에서 생기는 스트림 시작(디코더 시작)이다. 즉 실패는 시작 0.7 s 안의 일이다. 측정 구간을 바꾸면 통과할 수도 있지만, 결과를 본 뒤 정의를 바꾸지 않는다.

### 2.6 120 fps(선택지, 결정 0045)
