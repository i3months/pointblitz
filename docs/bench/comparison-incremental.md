# 증분 three.js 기준(B1·B2) 비교 결과 — Rust·wgpu·wasm 의 몫

- 날짜: 2026-10-09. 계획 [comparison-plan-2.md](comparison-plan-2.md)(측정 전 고정), 결정 [0048](../decisions/0048-incremental-baselines.md).
- 장비: 한 PC(RTX 4070, i7-13700F, Windows 11, 60 Hz), 루프백. Chrome 155.0.8059.40, 드라이버 591.86. 데이터 flight-01(14 스냅샷, 마지막 2,502,015 점).
- 세션: **p48**(01:06–01:42, 10 대상 × cold 5 · orbit 5 · replay ×60 3 = 130 회) — 모두 첫 시도 C1–C4 유효, C2 오염 0. **p48-orbit**(01:44–01:53, 회전만 10 대상 × 5 = 50 회 다시) — 모두 첫 시도 유효. 값은 실행별 값의 중앙값(최소–최대, 실행 수).
- 대상: B0 = 0005 기준(PLY 전체, 메인 스레드 해석), **B1a·B1b** = three.js + PointBlitz 와 같은 청크 경로(올리기 (a) 두 번 / (b) 나눠 복사), **B1-webgpu** = B1a 를 three.js WebGPURenderer 로, **B2** = SkyLens 식 증분 PLY + 워커 해석, PointBlitz web(WebGPU)·webs(WebGPU 전용 모듈)·webgl(WebGL2)·native·video.

## 1. 한눈에
- **구조(증분·GPU 배치 바이너리 전달)의 몫이 거의 전부다.** B0 → B1 만으로 미리보기 451 → 30 ms(15 배), 정밀 599 → 117 ms(5.1 배), cold 893 → 130 ms(6.9 배), 메인 스레드 멈춤 14 → 1–2 회, 렌더러 메모리 971 → 199 MB.
- **같은 구조에서 Rust·wgpu·wasm 의 몫은 지연에서 측정 흔들림 안이다.** 같은 API 끼리: WebGL2 에서는 three.js(B1*)가 PointBlitz webgl 보다 미리보기·정밀·cold 모두 빠르거나 같고(0.72–0.92 배), WebGPU 에서는 PointBlitz web 이 three.js(B1-webgpu)보다 1.12–1.26 배 빠르다. 남는 차이는 메인 스레드 멈춤(PointBlitz web 0 회, B1* 1 회)과 메모리 조금(WebGPU 끼리 1.55 배)이다.
- **해석도 Rust 가 빠르지 않다.** 잘 짠 JavaScript 워커는 250만 점 PLY 를 16.4 ms 에 해석한다(같은 스냅샷을 Rust 서버가 파일에서 읽는 데 22.5 ms). §5.
- **SkyLens 식으로 잘 만든 three.js(B2)도 PointBlitz 와 가깝다**: 미리보기 36.0 대 29.3 ms, 정밀 162 대 127 ms, cold 184 대 134 ms. 다만 메모리 354 대 183 MB, 받는 데이터 304 대 180 MB.
- **그리기(frame_time)는 깨끗한 같은 API 비교가 없다**: PointBlitz webgl 의 frame_time 은 측정 결함(§4.2, P4.6 부터), WebGPU 는 두 모드로 나뉘어(§4.1) 하나의 숫자로 판정하지 않는다. 진단 값으로는 WebGPU 끼리 PointBlitz 1.4 대 three.js 2.1 ms/프레임(batch=30), WebGL2 끼리 three.js 1.6–1.7 대 PointBlitz 약 4.5–5 ms(정상 상태).

### 4.1 WebGPU 동기화의 두 모드(결정 0048 규칙 (나) 적용)
- 모양: 느린 모드가 나오면 **늘 시점 5(동기화 481 번째 프레임)부터** 시점 5–8 이 한 값에 몰린다 — web·webs 15.5–15.8 ms, B1-webgpu 9.3–13 ms. 시점 1–4 는 약 3 ms.
- 빈도: p48 에서 web 5/5, webs 5/5(1 회는 시점 5 만), B1-webgpu 5/5. p48-orbit 에서 각 1/5. 감독 측정(2026-10-08 23:06)에서 web 1/1. **P4.6(2026-10-08)에서는 web·webs 0/10.** 오늘 진단 12 회(web·B1-webgpu, batch 1·30)에서 0/12.
- 확인: ① 분포 — 시점 중앙값이 한 값에 몰림(그리기 비용이면 시점마다 달라야 함). 다만 느린 모드 실행의 프레임별 원시 기록은 없다(제품 측정은 원시 기록을 남기지 않았고, 진단에서는 재현되지 않음). ② batch=30 으로 느린 모드에서 돌아오는지는 **재현되지 않아 확인 못 함**. ③ 클럭: 느린 모드 실행의 평균 클럭 약 1,400 MHz, 빠른 실행 2,339 MHz — 기다리는 동안 GPU 가 쉬어 내려간 결과인지 원인인지는 가리지 못했다.
- 그래서 규칙 (나): 두 세션 값을 모두 싣고 **"WebGPU 동기화 frame_time 은 약 3 ms / 약 10–15 ms 두 모드로 나뉨, 원인 미확인"** 으로 쓴다. 빠른 모드의 약 3 ms 도 대부분 동기화(1 픽셀 복사 + mapAsync) 비용이다: 같은 날 batch=30(30 프레임마다 한 번 동기화) 진단은 **web 1.4 ms, B1-webgpu 2.1 ms/프레임**(각 3 회, 시점 8 곳 모두 같은 값대).

### 4.2 PointBlitz webgl 의 frame_time 은 측정 결함(P4.6 부터)
- 시점 1–4 가 0.0–0.2 ms, 시점 5–8 이 3.7–5.3 ms(p48·p48-orbit·P4.6 모두 같은 모양). 진단: `cpu`(= `render_offscreen()` 호출) 와 `ms`(동기화까지)가 같다 — 1 픽셀 `readPixels` 가 기다리지 않는다. readPixels 는 캔버스(기본 프레임버퍼)를 읽는데 PointBlitz 는 화면 밖 텍스처에 그리므로, 드라이버가 그 그리기를 기다릴 이유가 없다. 처음 약 420–480 프레임은 GPU 작업이 쌓이기만 하고(0.1 ms), 큐가 차면 제출이 막혀 그 뒤로는 처리 속도(약 4.5–5 ms)가 보인다.
- 그래서 P4.6 에 공개한 webgl frame_time(3.5 / 6.0 / 13.5 ms)은 그리기 비용이 아니라 두 상태의 섞임이다. 정상 상태(시점 5–8) 값으로 보면 **PointBlitz WebGL2 는 약 4.5–5 ms/프레임, 같은 WebGL2 의 three.js(B1)는 1.6–1.7 ms** — 같은 API 에서 three.js 가 빠르다. 측정 고침(화면 밖 텍스처를 읽는 동기화)은 다음 일로 남긴다.

## 6. 공개 문구에 주는 뜻(소유자 결정 사항)
- 지금 공개한 "새 데이터가 화면에 5–23 배 빨리" 는 **증분 없는 three.js(B0) 대비**이고, 그 몫은 거의 모두 구조(증분·바이너리 전달·해석 없음)에서 온다.
- 같은 구조의 three.js 대비 Rust·wgpu·wasm 의 지연 이득은 측정 흔들림 안이다. 메인 스레드 멈춤 0 회(WebGPU)와 약간 적은 메모리는 남는다. 그리기는 WebGPU 에서 PointBlitz 가 빠르고(진단 1.4 대 2.1 ms), WebGL2 에서는 three.js 가 빠르다(진단 1.6–1.7 대 4.5–5 ms).
