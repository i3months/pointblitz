# 비용 모델 (P4.5) — 1 단계: RTX 4070 보정

- 상태: **두 장비 보정 끝**(RTX 4070 PC + V100 서버, §4, 결정 0043). CPU 청크 만들기와 NVENC 는 두 장비 비로 추정하고, GPU 그리기는 두 장비가 같은 수준이라 다른 GPU 로 옮기는 기준을 아직 정하지 못했다(§4·§5). 1–3 절의 계수는 RTX 4070 PC 값이다.
- 방법: 결정 0011 — 단계마다 하드웨어와 무관한 양(바이트·점·픽셀·프레임)과, 그것을 좌우하는 하드웨어 값을 짝짓는다. 두 장비로 계수를 맞춘 뒤 다른 장비는 공개 사양으로 추정한다.
- 데이터: `flight-01` 마지막 스냅샷(2,502,015 점, PLY 67,554,652 B, 청크 40,033,040 B), P3.4 같은 세션 측정(`docs/bench/server-video.md`), P4.1 동기화 분리.

그리기 1.37 ms 에서 정점 데이터는 40 MB 를 읽는다(약 29 GB/s) — RTX 4070 의 메모리 대역폭(504 GB/s)보다 훨씬 작으므로 메모리가 아니라 **정점 처리·래스터 처리량**이 한계다. 다른 GPU 추정은 이 처리량(대략 FP32 연산 성능에 비례)으로 비례시킨다는 처음 가정은 **V100 보정에서 맞지 않았다**(§4: FP32 절반인 V100 이 서버 렌더는 같음).

## 2. 모델 (한 스냅샷이 화면에 나오기까지)

- **three.js**: `T = 전송(PLY 바이트 / 네트워크) + 해석(PLY 바이트 / CPU 해석 속도) + 업로드(36 B/점) + 그리기`
- **PointBlitz native·browser**: `T = 서버 읽기 + max(변환, 전송(청크 바이트 / 네트워크)) + 마지막 청크 업로드 + 다음 프레임`
  (변환과 전송은 청크 단위로 겹친다. preview 는 차분 청크만 보낸다.)
- **server video**: `T = 서버 읽기 + 변환 + 서버 GPU 업로드 + 다음 틱(≤ 16.7 ms) + 렌더 + 인코딩 + 전송(프레임 바이트 / 네트워크) + 디코딩`

## 3. 네트워크별 추정 — 클라이언트 렌더 대 서버 영상 (이 PC 의 CPU·GPU 를 그대로 두고 네트워크만 바꿈)

네트워크 외의 항은 1 절의 이 PC 값이다. 네트워크 항만 바꾼 **추정**이다(측정 아님).

server video 의 네트워크 항은 스냅샷을 처음 보여 주는 프레임 하나다. 2026-10-08 replay ×60 실측(immediate 3 회, 41 개, `bench/video/frame-bytes.mjs`): p50 13.9 KiB, 최대 171.0 KiB. 표는 최대 크기로 계산했다(1 Gbps 1.4 ms, 100 Mbps 14 ms, 20 Mbps 70 ms).

| 마지막 스냅샷(refined, 전체) 반영 | 루프백(실측) | 1 Gbps | 100 Mbps | 20 Mbps |
|---|---:|---:|---:|---:|
| three.js(PLY 67.6 MB) | 909 ms | 약 1.4 s | 약 6.2 s | 약 28 s |
| PointBlitz native·browser(청크 40.0 MB) | 167–187 ms | 약 0.35 s | 약 3.2 s | 약 16 s |
| server video(교체 프레임, 실측 최대 171 KiB) | 175 ms | 약 0.18 s | 약 0.19 s | 약 0.25 s |

기준: ×60 replay 의 preview 반영 **p50**. preview 7 회 중 가운데는 `preview_3`(PLY 33.4 MB, 새 점 약 4.5 만 = 차분 약 0.71 MB)이므로, 네트워크 항도 이 스냅샷의 바이트로 계산한다(실측에서 루프백 전송 몫을 빼고 대역폭별 전송을 더함).

|---|---|---|---|
| 클라이언트 렌더(native·browser) | 받을 것 없음(로컬 GPU) | 같음 | 같음 |

**읽는 법**
- 대역폭이 크면(같은 LAN·데이터센터) 세 방식 모두 빠르고, 차이는 해석(three.js)과 그리기 위치다.
- 대역폭이 작아질수록 **전체 스냅샷을 보내는 방식(three.js, refined 의 PointBlitz 클라이언트)은 선형으로 느려지고**, server video 는 반영 시간이 거의 그대로다(보내는 것이 화면뿐). 대신 server video 는 회전 중 영상 대역폭이 필요하다.
- 소유자 방침(대역폭·메모리는 제약이 아님)에서는 LAN·데이터센터를 기본으로 보고, 저대역폭은 참고로 싣는다.

## 4. 두 번째 장비: V100 서버(소유자 제공) — 같은 방법으로 두 장비 (결정 0043)

두 장비에서 헤드리스로 똑같이 잰 것(`bench/two-machine.sh`, 2026-10-08): ① 재생 서버가 마지막 스냅샷(40.0 MB)을 청크로 만들어 루프백으로 보냄 5 회, ② `serve --orbit`(cold 적재 + 720 회전 프레임) + 헤드리스 클라이언트 5 회, ③ `encode-test`(고정 시점·회전 각 240 프레임, QP 18). 클라이언트는 디코딩하지 않고 6 프레임 뒤 끊으므로, 서버의 틱마다 렌더·인코딩 비용만 잰다(보내기 제외 — 두 장비 같음).

| | RTX 4070 PC(i7-13700F, Windows) | V100 서버(Xeon Gold 6140 2.3 GHz 16 코어, Linux) | V100 ÷ 4070 |
|---|---:|---:|---:|
| 청크 만들기: 스냅샷 읽기·변환(40.0 MB) | 18.3–20.1 ms | 44.6–51.9 ms | **약 2.6** |
| 청크 전체 전달(루프백) | 54–176 ms(다시 8 회: 59–99 ms) | 96.8–100.9 ms | — |
| 서버 렌더(그리기 + 화면 읽어 오기) p50 | 5.50–6.14 ms | 5.62–5.86 ms | **약 1.0** |
| 서버 인코딩(입력 복사 + NVENC) p50, `serve` | 3.83–5.36 ms | 5.25–5.44 ms | 약 1.0–1.4 |
| 인코딩만(`encode-test` 회전) p50 | 2.81 ms | 3.59 ms | **1.28** |
| NVENC 입력 복사(upload) p50 | 0.62 ms | 1.80 ms | **2.9** |
| 화면 읽어 오기 포함 렌더(`encode-test` capture) p50 | 3.54 ms | 5.57 ms | 1.57 |
| 늦은 틱(`serve`) | 0–3 / ~790 | 1–5 / 785 | — |

**읽는 법(두 장비로 맞춘 계수)**
- **CPU 쪽(청크 만들기)**: 잰 비는 **2.6 배**다. 두 CPU 의 최대 단일 스레드 클럭 비(5.2 대 3.7 GHz)는 **1.4 배**뿐이라 클럭만으로는 설명되지 않고, 나머지(세대 차·캐시·메모리·가상 머신 등)는 **원인 미확인**이다. "단일 스레드 성능 비로 추정한다" 는 두 점으로는 확인되지 않았다 — 다른 장비 값은 추정하지 않고 두 장비 값 사이·바깥이라고만 적는다.
- **청크 전체 전달의 흔들림(RTX 4070 PC 54–176 ms, V100 서버 97–101 ms)**: 읽기는 두 장비 모두 고르다(18–20 ms, 45–52 ms). 흔들림은 보내기(루프백 TCP 로 40 MB 를 보내는 쪽)다. 이 PC 에서 1 초 간격으로 8 회 다시 재면 합계 59–99 ms, 받는 쪽 속도 395–622 MB/s 로 흔들렸고, 처음 측정의 155–176 ms 는 재현되지 않았다 — Windows 루프백 전송 속도의 흔들림으로 보며 원인은 확인하지 못했다.
- **GPU 그리기는 FP32 성능을 따르지 않는다**: V100 의 FP32(약 14 TFLOPS)는 RTX 4070(약 29)의 절반인데 서버 렌더는 같았다. 메모리 대역폭(V100 900 대 504 GB/s)만으로도 설명되지 않는다 — 이 크기(2.5 M 점, 1920×1080)에서는 그리기보다 화면 읽어 오기·PCIe(V100 서버는 PCIe 3 대 4070 의 PCIe 4: upload 2.9 배)가 비슷한 몫을 차지한다. 1 절의 "FP32 에 비례" 가정은 맞지 않아 버린다. 다른 GPU 의 그리기 추정은 이 두 점만으로는 어느 하드웨어 값에 비례하는지 정할 수 없다 — **추정하지 않고 "두 장비 범위(같은 수준)" 로만 적는다**.
- **NVENC 는 세대를 따른다**: 인코딩만 1.28 배(Volta 6 세대 대 Ada 8 세대 NVENC). 60 fps 예산(16.7 ms) 안에 두 장비 모두 넉넉하다.
- 서버 영상 한 틱(렌더 + 인코딩)은 두 장비 모두 약 11 ms 로 60 fps 를 지킨다.

**측정 조건과 사고**
- V100 은 소유자 계정의 다른 GPU 작업과 같이 쓰는 장비다. 첫 시도(17:38–17:40)는 소유자 계정의 다른 GPU 작업이 도중에 시작해 겹쳤다(`serve` 5 회 중 3 회 늦은 틱 4–12 %) — **버리고**, 소유자 지시("내 작업 우선")로 그 작업을 멈추고, 다른 작업들이 쓰는 GPU 잠금 파일을 잡은 채 다시 쟀다(17:43–17:46). 이 값이 위 표다.
- V100 쪽 C3(화면 없음)은 해당 없고, C4 는 Windows 보정 도구가 없어 미상이다(env.txt 에 CPU·부하 기록). 기록: target/bench/p45-v100(로컬).
- Linux NVENC 왕복: `encode-test` 출력(회전·고정 각 240 프레임)을 V100 서버의 ffmpeg 로 디코딩 — H.264 High, 1920×1080, 240 프레임, 오류 0.

## 5. 남은 것
- 그리기 계수를 정하려면 세 번째 점(다른 세대·다른 메모리 대역폭의 GPU)이 필요하다. 지금은 두 장비 모두 같은 수준이라는 것까지만 말한다.
- native 창·브라우저는 V100 서버에서 잴 수 없다(화면 없음).
