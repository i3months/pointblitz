# PointBlitz 성능 보고서 — 기존 three.js 방식 대비

- 날짜: 2026-10-08
- 근거: [comparison.md](comparison.md)(P4.6 같은 세션 비교), [baseline-three.md](baseline-three.md), [diagnostics.md](diagnostics.md), [server-video.md](server-video.md), [cost-model.md](cost-model.md), [validity-audit.md](validity-audit.md)

**새 데이터가 화면에 나오기까지 걸리는 시간이 기존 three.js 방식보다 미리보기(preview)는 13–23배, 정밀 스냅샷(refined)과 첫 화면(cold)은 5–7배 짧아졌습니다.** 같은 데이터를 받는 양은 66 % 줄었고(서버 영상은 98 %), 브라우저 메인 스레드 멈춤은 14 회에서 0 회로, 브라우저 렌더러 메모리는 965 MB 에서 166–215 MB 로 줄었습니다.

그리기 속도는 빨라지지 않았습니다. 데스크톱(native)은 기존과 같은 수준(프레임당 1.55 대 1.70 ms)이고, 브라우저는 매 프레임 GPU 와 동기화하는 비용 때문에 목표에 못 미칩니다(3.1 ms). 빨라진 이유는 그리기가 아니라 데이터 경로입니다: 브라우저에서 파일 해석을 없애고, GPU 에 바로 올릴 수 있는 형태로 새 점만 보냅니다.

측정: 한 PC(RTX 4070, i7-13700F, Windows 11), 서버와 클라이언트가 같은 PC(루프백), SkyLens 비행 데이터 flight-01(스냅샷 14 개, 마지막 250만 점), 2026-10-08 같은 세션에서 여섯 구현을 번갈아 측정. 네트워크가 느릴 때와 다른 장비는 뒤의 "네트워크가 느릴 때" 절에 있습니다.

## 왜 빨라졌나

**기존 방식은 스냅샷마다 PLY 파일 전체를 다시 받아 브라우저 메인 스레드에서 해석했고, 그 해석이 시간의 대부분이었습니다.** PointBlitz 는 서버가 한 번 만든 GPU 용 청크를 보내고, 미리보기는 새 점만 보내며, 클라이언트는 받은 바이트를 해석 없이 GPU 에 올립니다.

마지막 스냅샷(250만 점)이 화면에 나오기까지의 단계별 시간입니다(cold 5 회 중앙값, native 는 단계별 기록이 있는 대상).

| 단계 | three.js(기존) | PointBlitz native |
|---|---|---|
| 파일 읽기·청크 만들기(서버) | — | 19 ms |
| 받기 | 115 ms(PLY 67.6 MB) | 164 ms(청크 40.0 MB, 변환과 겹침) |
| 해석(브라우저 메인 스레드) | **740 ms** | 0 |
| GPU 에 올리기 | 나머지에 포함 | 10 ms(도착하는 대로, 마지막 청크 뒤엔 0.5 ms) |
| 다음 프레임 | 나머지에 포함 | 2 ms |
| **합계** | **904 ms** | **186 ms** |

빨라진 이유를 크기 순으로 보면 다음과 같습니다.

1. **해석이 사라졌다.** three.js 는 PLY 를 메인 스레드에서 초당 약 89 MB 속도로 해석합니다. cold 에서 740 ms(전체의 82 %), 재생 전체에서는 6.2 초이고, 그동안 화면과 입력이 멈춥니다(50 ms 넘는 멈춤 14 회). PointBlitz 청크는 GPU 버퍼의 배치 그대로라 브라우저에서 해석이 0 ms 이고, 멈춤도 0 회입니다.
2. **미리보기는 새 점만 보낸다.** skyrecon 의 미리보기 스냅샷은 앞 스냅샷에 점을 더한 것이라, 더해진 점만 보냅니다. 보내는 양이 0.35–0.87 MB 로, PLY 전체(4.1–65.5 MB)보다 최대 189 배 작습니다. 그래서 미리보기 지연은 점이 늘어도 15–35 ms 에 머물고, three.js 는 78 ms 에서 914 ms 로 늘어납니다(앞 절의 표).
3. **보내는 형식이 작다.** 점 하나가 PLY 는 27 바이트, 청크는 16 바이트라 같은 스냅샷도 41 % 작습니다. 재생 전체로는 2와 합쳐 530.8 MB 가 180.4 MB 가 됩니다.
4. **도착하는 대로 올린다.** 스냅샷은 청크 10 개로 오고, 청크가 올 때마다 GPU 에 올립니다. 마지막 청크가 도착한 뒤에 남는 일은 0.5 ms 업로드와 한 프레임뿐입니다.
5. **정밀 스냅샷은 세대 교체로 바꾼다.** 정밀 스냅샷은 점 전체가 다시 계산되므로 전부 다시 받되, 다 올 때까지 이전 화면을 유지하다가 한 번에 바꿉니다(빈 화면 없음). 이때 시간의 대부분(186 ms 중 164 ms)은 40 MB 를 보내는 시간이라, 네트워크가 느리면 그만큼 늘어납니다("네트워크가 느릴 때" 절).
6. **메모리가 적다.** three.js 는 해석한 배열을 JavaScript 힙에 들고 있어(452–478 MB) 렌더러가 965 MB 까지 커집니다. PointBlitz 브라우저의 힙은 2–3 MB 입니다. 메모리는 목표가 아니라 기록입니다.

## 그리기 속도는 왜 같은 수준인가

**그리기는 빨라지지 않았고, 빨라질 여지도 작았습니다.** 두 방식 모두 같은 GPU 가 같은 250만 점을 1920×1080 화면에 그리고, 기존 three.js 도 그리기 자체는 GPU 에서 효율적으로 합니다. 판정 값(프레임마다 GPU 가 끝날 때까지 기다린 시간)은 native 1.55 / 1.81 / 2.00 ms, three.js 1.70 / 1.90 / 2.0 ms 로, native 가 목표(기존 방식 이하)를 지키지만 p99 는 여유가 없습니다.

| 프레임 시간 p50 / p95 / p99 (ms) | 매 프레임 동기화(판정 값) | 30 프레임마다 동기화(진단 값) |
|---|---|---|
| three.js(기존) | 1.70 / 1.90 / 2.0 | — |
| native | 1.55 / 1.81 / 2.00 | 1.37 / 1.56 / 1.61 |
| 브라우저 WebGPU | 3.1 / 4.3 / 5.0 | 1.43 / 1.61 / 1.65 |
| 브라우저 WebGL2 | 3.5 / 6.0 / 13.5 | 3.80 / 5.22 / 6.38 |

- **브라우저 WebGPU 의 미달은 그리기가 아니라 기다리는 비용입니다.** 매 프레임 GPU 가 끝났는지 확인하려면 1 픽셀을 복사해 읽어 오는 왕복(Chrome 의 GPU 프로세스를 거침)이 필요합니다. 30 프레임마다 한 번만 확인하면 1.43 ms 로 native(1.37 ms)와 거의 같습니다.
- **WebGL2 는 CPU 쪽에서 느립니다.** 동기화를 나눠도 줄지 않고(3.8 ms), 비용은 GL 명령을 Chrome → ANGLE → Direct3D 11 로 보내는 제출 단계에 있습니다. cold 에서 메인 스레드를 한 번 막는 것도 같은 경로입니다.
- 화면은 바뀐 것이 있을 때만 그립니다. 60 Hz 화면의 한 프레임은 16.7 ms 라 네 구현 모두 여유가 크며, 회전이 끊기지는 않습니다.
- three.js 의 프레임 시간은 그날 GPU 클럭 상태에 따라 세션마다 1.7–2.8 ms 로 흔들렸습니다. 그래서 비교는 같은 세션의 값만 씁니다(측정 절).

## 서버 영상

**서버가 그리고 하드웨어로 압축한 화면만 보내는 방식은 모든 SPEC 목표를 지켰고, 받는 데이터는 기존의 2 %(530.8 MB → 10.3 MB)입니다.** 브라우저는 영상만 풀어 보여 주므로 점 개수와 상관없이 메모리 46 MB 로 돌아갑니다.

| 서버 영상 (화면에 나온 시각 기준) | 값 | 목표 |
|---|---|---|
| 미리보기 / 정밀 / cold | 23 / 118 / 156 ms | 80 / 250 / 350 ms |
| 입력 → 화면 p50 / p95 (회전 중) | 23 / 33 ms | 50 / 80 ms |
| 화질 SSIM(데스크톱 화면 대비, 고정 시점 8 곳) | 0.9967 | ≥ 0.95 |
| 프레임 빠짐(회전 중) | 중앙값 0.40 %, 5 회 중 2 회 > 1 %(최대 6.32 %) | ≤ 1 % |
| 서버 한 프레임(그리기 + 압축) | 약 11 ms | 60 fps = 16.7 ms |
| 회전 중 비트레이트 | 약 75 Mbps(화질 우선 설정) | 기록만 |

- **프레임 빠짐은 프레임을 잃는 것이 아닙니다.** 서버는 정확히 60 Hz 로, 화면은 60 Hz 보다 조금 느리게 돌아 도착 시각이 화면 갱신 경계를 지나갈 때, 한 주기가 비고 다음 주기에 두 장이 모입니다.
- **측정 중 찾아 고친 결함 둘:** ① 디코더가 프레임을 약 70 ms 잡아 두던 것(스트림에 "다음 프레임 참조 없음" 표시를 넣어 없어짐), ② 서버가 프레임을 16.7 ms 가 아니라 Windows 타이머 격자(15.6 ms)에 맞춰 보내던 것(쓰기 스레드로 바로 보내게 고침: 빠짐 중앙값 8.14 % → 0.79 %, 입력 → 화면 36 → 33 ms).
- **시도했지만 기본값이 되지 못한 것:** 브라우저가 한 프레임을 쌓아 두는 버퍼(끊김은 없애지만 입력 지연이 수용 기준 40 ms 를 넘음), 서버 틱을 화면에 맞추는 위상 잠금(끊김을 거의 없애고 지연도 줄였지만 연결 직후 0.7 초의 빠짐 때문에 미리 정한 기준을 두 번 못 맞춤). 둘 다 선택지로 남아 있습니다.
- 서버 영상은 네트워크가 느릴수록 유리해집니다. 스냅샷 크기와 무관하게 화면만 보내기 때문입니다(다음 절). 대신 회전 중에는 계속 약 75 Mbps 가 필요합니다.

## 네트워크가 느릴 때(추정)와 두 번째 장비

**위 측정은 네트워크 시간이 거의 없는 같은 PC 안에서 쟀으므로, 실제 네트워크에서는 격차가 더 벌어집니다.** 아래는 측정한 단계별 속도에 네트워크 전송 시간만 바꿔 넣은 **추정**입니다(측정 아님, [비용 모델](cost-model.md)).

| 마지막 정밀 스냅샷이 화면에 | 같은 PC | 1 Gbps | 100 Mbps | 20 Mbps |
|---|---|---|---|---|
| three.js(기존, PLY 67.6 MB) | 0.9 초 | 약 1.4 초 | 약 6.2 초 | 약 28 초 |
| PointBlitz 브라우저·native(청크 40.0 MB) | 0.2 초 | 약 0.35 초 | 약 3.2 초 | 약 16 초 |
| 서버 영상(화면 한 장, 최대 171 KB) | 0.2 초 | 약 0.18 초 | 약 0.19 초 | 약 0.25 초 |

| 미리보기가 화면에(중앙값 스냅샷) | 같은 PC | 1 Gbps | 100 Mbps | 20 Mbps |
|---|---|---|---|---|
| three.js(기존, PLY 33.4 MB) | 0.46 초 | 약 0.66 초 | 약 3.1 초 | 약 14 초 |
| PointBlitz 브라우저·native(새 점 약 0.71 MB) | 20–27 ms | 25–30 ms | 75–85 ms | 약 0.3 초 |
| 서버 영상 | 15 ms | 15–20 ms | 약 20 ms | 20–30 ms |

- 기존 방식은 파일 전체를 보내므로 네트워크가 느릴수록 그대로 느려집니다. PointBlitz 미리보기는 새 점만 보내서 20 Mbps 에서도 약 0.3 초이고, 서버 영상은 거의 그대로입니다.
- 서버 영상은 회전 중에 약 75 Mbps 가 필요해, 20 Mbps 에서는 화질을 낮춰야 합니다(화질 설정을 한 단계 낮추면 36 Mbps, SSIM 0.988).

**두 번째 장비(V100 서버, 소유자 제공, Linux)** 에서 같은 방법으로 재 보니, 서버 그리기는 RTX 4070 과 같은 수준(5.6–5.9 대 5.5–6.1 ms), 영상 압축은 1.28 배, CPU 의 청크 만들기는 2.6 배 느렸습니다. 두 장비 모두 서버 영상 한 프레임이 약 11 ms 로 60 fps 를 지킵니다. GPU 연산 성능이 절반인 V100 이 같은 속도로 그렸기 때문에, 다른 GPU 의 그리기 속도를 어떤 사양으로 추정할지는 아직 정하지 못했습니다.

## 측정을 어떻게 믿을 수 있게 했나

**다른 날 잰 값끼리 비교하지 않고, 여섯 구현을 한 세션에서 실행마다 번갈아 쟀습니다(78 회, 2026-10-08 15:38–15:59).** 측정 도중 PC 상태가 결과를 바꾼다는 것을 세 번 찾았고, 그때마다 규칙을 만들어 그 전 값을 다시 재거나 "조건 미상" 으로 표시했습니다.

| 규칙 | 무엇을 막나 | 찾은 계기 |
|---|---|---|
| C1 GPU 경합 | 실행 전 GPU 를 다른 작업이 쓰고 있으면 무효 | 감독 세션의 재현 측정과 겹침 |
| C2 서버 튐 | 서버 그리기·압축이 같은 시나리오의 두 배를 넘으면 무효 | 서버 영상 측정 |
| C3 화면 시계 | 화면 갱신이 59.5–60.5 Hz 밖이면 무효 | 아무도 PC 를 안 쓸 때 모니터가 꺼지면 브라우저의 화면 시계가 56.6 Hz 로 떨어짐 |
| C4 CPU 상태 | CPU 보정값이 기준의 90 % 미만이면 무효 | Windows 절전 기능(EcoQoS)이 백그라운드 측정 프로세스를 효율 코어로 옮겨 해석이 절반 속도가 됨 |

- 모든 실행은 측정 동안만 화면을 켜 두고, 측정 프로세스에만 절전을 끕니다(시스템 설정은 바꾸지 않음). 실패하거나 무효인 실행은 같은 조건으로 한 번만 다시 돌리고, 첫 시도 파일은 남깁니다. 이 보고서의 78 회는 모두 유효했고, 다시 돌린 것은 1 회입니다.
- **기준값도 고쳤습니다.** 기존 방식의 프레임 시간 목표(2.8 / 3.8 / 6.0 ms)를 정한 처음 측정은 14 회 중 11 회가 모니터가 꺼진 상태(C3 무효)였습니다. 다시 잰 값 1.7 / 1.9 / 2.0 ms 로 목표를 엄격하게 고쳤고, PointBlitz 에 불리한 쪽입니다.
- 판정 기준도 공정하게 맞추었습니다. 예를 들어 서버 영상의 지연은 "그린 시각" 이 아니라 화면에 나온 시각으로 잽니다(예전 방식은 한 방식에 약 8 ms 유리했음).
- 이전 단계의 판정은 지우지 않고 "조건: C4 미상" 으로 남겨 두었습니다. 모든 기술 선택은 결정 기록(0001–0043)에, 검토는 PR 마다 별도 감독 세션이 재현 측정으로 했습니다.

## 한계와 남은 일

**이 수치는 한 PC 와 한 비행 데이터의 결과이고, 두 가지 목표 미달과 한 가지 주의가 남아 있습니다.**

- **미달:** 브라우저의 프레임 시간(매 프레임 동기화 비용), WebGL2 의 cold 메인 스레드 멈춤 1 회.
- **주의:** 서버 영상 프레임 빠짐은 중앙값으로 통과하지만 5 회 중 2 회가 1 % 를 넘습니다.
- **측정 범위:** 서버·클라이언트 같은 PC(네트워크는 추정만), 비행 데이터 하나(flight-01), 브라우저는 Chrome, 화면은 60 Hz. V100 서버는 화면이 없어 서버 쪽 측정만 했습니다.
- **남은 일:** ① 대외 공개(npm 패키지 배포, README 밖의 알림)는 소유자 결정(P4.8) ② 다른 GPU 의 그리기 속도를 추정하려면 세대·메모리 대역폭이 다른 세 번째 GPU 측정이 필요 ③ 다음 단계 P5(메시, Python 바인딩).
