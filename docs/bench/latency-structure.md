## 3. 단계 분해
### 3.1 web 정밀 스냅샷(재생, 원시 마크, 실행·스냅샷 중앙값, 알림 수신 기준 ms)
- before: fetch_start 0.00 → headers 17.7 → first_chunk 32.9 → last_chunk_received 91.3 → uploaded 91.7 → presented 116
- after: fetch_start 0.00 → headers 2.15 → first_chunk 35.8 → last_chunk_received 96.5 → uploaded 97.2 → presented 123

- 응답 머리(headers)는 17.7 → 2.2 ms 로 빨라졌다(요청마다 디스크에서 읽던 약 18 ms 가 빠짐). 그러나 첫 청크는 32.9 → 35.8 ms, **마지막 청크 도착은 91.3 → 96.5 ms 로 그대로**다 — 변환은 알림 때 시작했지만 요청이 몇 ms 뒤에 와서 대부분 "진행 중" 이었고, 40 MB 를 브라우저가 받는 시간이 남는다.

### 3.2 재생 서버(변경 후 로그)
- 요청 450 건 중 변환이 **진행 중** 402, **끝나 있음** 47, **새로 시작** 1(알림 없는 cold 첫 요청). 정밀 스냅샷 14(40 MB): 파일 읽기 18.6 ms, 인코딩 끝 27.5 ms(변환 시작부터), 요청 처리 total 65–120 ms. 변경 전은 같은 스냅샷 읽기 18.3–19.6 ms, total 121–174 ms.

### 3.3 브라우저 받기 바닥(40 MB 정적 파일, 같은 세션)
- 받기 바닥(start): 40 MB 중앙값 50.5 ms (44.6–111, 5 회)
- 받기 바닥(end): 40 MB 중앙값 68.1 ms (40.5–106, 5 회)

## 5. 결론
- **서버 영상이 크게 빨라졌다**: 정밀 115 → 58.5 ms(1.96 배 [1.66–2.25]), cold 160 → 46.0 ms(3.46 배 [2.69–4.18]). 영상 서버가 HTTP 로 청크를 받던 단계가 없어진 몫이다(①).
- **native·webgl**: 정밀 1.16·1.18 배, cold 1.17·1.70 배 빨라짐(구간이 1 보다 큼). 응답 머리가 빨라진 몫과 메모리에서 바로 보내는 몫이다(②).
- **web(WebGPU)**: 미리보기·정밀·cold 모두 차이 없음. 브라우저가 40 MB 를 받는 시간(같은 세션 40–111 ms)이 바닥이다 — 결정 0051(바이트 줄이기·거친 것 먼저)의 근거다.
- 미리보기(차분, 0.4–0.9 MB)는 모든 대상에서 차이 없음.
