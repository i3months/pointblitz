# 측정 계획 4 — 지연 구조 변경 전후(P4.11, 측정 전 고정)

- 날짜: 2026-10-09. [결정 0050](../decisions/0050-latency-structure.md), 판정 규칙은 [결정 0049](../decisions/0049-remove-remaining-ambiguity.md) §3 그대로. 바꾸려면 측정 전에 이 문서를 고친다.

## 순서
1. 구현 PR(P4.9·P4.10) 병합 → 이 계획과 측정 스크립트 PR 병합.
2. 측정 전 대기 GPU 확인(5 초 간격 2 분 평균 ≤ 15 %, 아니면 시작하지 않고 감독에게 알림) → 측정 → 시작·끝 알림.
3. 결과 문서와 판정.

## 대상·회수
- **변경 전** = main 0404a79(요청마다 변환, 영상 서버는 HTTP), **변경 후** = 구현 PR 병합 뒤 main(알림 때 변환·메모리 전송, 영상 서버는 `--data`).
- 두 빌드를 나란히 두고 각자의 재생 서버(포트 둘)를 띄운다. 대상: **web(WebGPU) · webgl · native · video**. 시나리오: **cold 10 회, replay ×60 10 회**.
- 한 회차마다 대상별로 변경 전·후를 이어서 돌리고, **회차마다 순서를 뒤집는다**(홀수 회차 전 → 후, 짝수 회차 후 → 전).
- 스크립트: `bench/ab.sh <변경 전 저장소> <ply 디렉터리> <출력>`(이름 `<대상>-<before|after>-<시나리오>-<회>`), 유효성·재실행은 `bench/suite.sh` 와 같다(gpu-watch, C1·C3·C4 실행마다, 1 회 재실행, C2 는 끝에).
- **브라우저 받기 바닥**: 같은 세션의 시작과 끝에 변경 후 재생 서버의 40 MB 정적 파일을 Chrome 이 받는 시간(`bench/fetch-floor.mjs`, 5 회씩) — 감독 요청.

## 지표와 판정
- 지표: 재생 미리보기 p50, 재생 정밀 p50, cold 마지막 스냅샷(화면 기준 이름이 있으면 그 값, 지금까지와 같은 정의), 메인 스레드 멈춤(기록), mem_cpu(기록).
- 판정: 대상·지표마다 **비 = median(변경 전) ÷ median(변경 후)**(1 보다 크면 빨라짐). 부트스트랩 10,000 번(씨앗 48049) 95 % 구간이 1 을 포함하면 "차이 없음", 1 보다 크면 "빨라짐", 작으면 "느려짐".

## 단계 분해(판정 아님)
- web: 원시 마크로 정밀 스냅샷마다 `snapshot_received → fetch_start → headers → first_chunk → last_chunk_received → uploaded → presented` 의 중앙값.
- 재생 서버: 요청마다 `conversion ready/running/new`, 파일 읽기, 인코딩 끝, 요청 처리 total(서버 로그).
- video: 서버 로그의 같은 단계(알림 → 청크 도착/로컬 변환 끝 → 화면에 보인 프레임).

## 그림 확인
- 변경 전 대 변경 후, 고정 시점 8 곳 SSIM: web(`bench/web/capture.mjs`)과 video(`bench/web/video-capture.mjs`). 그리기 코드는 바뀌지 않았으므로 1.0000(같은 그림)이어야 한다.

## 이 계획이 지키는 것
- 변환은 두 쪽 모두 측정 구간(알림 → 화면) 안에 있다(0050). 결과가 불리해도 그대로 싣는다.
