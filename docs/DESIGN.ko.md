# PointBlitz 설계 (초안 v0)

- 상태: 초안. 아래 "열린 질문" 이 정해지기 전에는 구현하지 않는다.
- 날짜: 2026-10-07

## 1. 목표

1. skyrecon 점군을 **기존 방식(three.js)보다 빠르게** 그리는 Rust + wgpu 렌더 라이브러리를 만든다.
2. 같은 렌더 코어를 **브라우저(wasm)·네이티브·서버(영상 전송)** 세 곳에서 돌린다.
3. 기존 방식과 세 방식을 **같은 데이터·같은 시점·같은 시나리오** 로 재서 비교표를 만든다.
   비교표는 "이 정도 하드웨어에서 이 정도 성능" 을 말할 수 있도록 하드웨어 비용 모델을 함께 낸다.
4. 오픈소스로 공개한다. three.js 로 큰 점군을 그리다 한계에 부딪힌 사람들이 대상이다.

범위 밖(지금은): 3D 가우시안 스플랫. 메시(관제탑 지형·건물, 텍스처 표면)는 코어 설계에서만 고려하고 구현은 뒤로 미룬다.

## 2. 입력 데이터 — skyrecon 점군

- 형식: 이진 리틀 엔디언 PLY, 점 하나 27 B — `x y z`(f32×3), `red green blue`(u8×3), `nx ny nz`(f32×3).
  좌표는 미터 단위 ENU(정렬 원점 기준).
- 기준 시나리오: 한 비행의 스냅샷 14개(97 s ~ 2053 s), 마지막 250만 점 · 67.5 MB, 합계 530.8 MB.

### 2.1 스냅샷 관계 (실측, 2026-10-07)

| 이벤트 | 점 수 | 직전 스냅샷 점이 그대로 남은 비율 | 새 점 |
|---|---:|---:|---:|
| 01 preview_0 | 151,510 | — | 151,510 |
| 02 refined_0 | 336,118 | 0 % | 336,118 |
| 03 preview_1 | 371,585 | 100 % | 35,467 |
| 04 refined_1 | 749,216 | 0 % | 749,216 |
| … | … | preview 는 늘 100 %, refined 는 늘 0 % | … |
| 13 preview_6 | 2,426,023 | 100 % | 21,611 |
| 14 refined_6 | 2,502,015 | 0 % | 2,502,015 |

- **preview 이벤트는 순수 추가다.** 직전 refined 를 그대로 두고 새 구역 점 2~5만 개(약 0.6~1.5 MB)만 붙는다.
- **refined 이벤트는 전체가 바뀐다.** 좌표가 비트 단위로 하나도 같지 않다. 정렬(BA·GPS 재정렬) 뒤 다시 조밀화했기 때문으로 보인다.
- 따라서 기존 방식(매번 전체 재다운로드·재파싱·재업로드)과 비교할 때 preview 는 증분 추가로 큰 차이가 나고,
  refined 는 "전체 교체를 얼마나 빨리 하느냐" 의 싸움이 된다.

## 3. 아키텍처

```
                 ┌──────────────────────────── pointblitz-core ───────────────────────────┐
skyrecon PLY ──► │ ingest(PLY 스트림 파서) → chunk store(append/replace) → GPU buffers     │
(파일·스트림)    │ → cull(절두체·옥트리) → LOD(화면 공간 크기) → draw(점 = 화면 정렬 사각형) │
                 └──────────────┬──────────────────────┬──────────────────────┬────────────┘
                                │                      │                      │
                     pointblitz-native        pointblitz-web (wasm)   pointblitz-server
                     winit 창                 canvas, WebGPU/WebGL2   헤드리스 → NVENC → 영상
```

### 3.1 크레이트

| 크레이트 | 역할 |
|---|---|
| `pointblitz-core` | 장면·청크·GPU 버퍼·컬링·LOD·렌더 패스·고정 시점 캡처. 창·네트워크에 의존하지 않는다 |
| `pointblitz-io` | PLY 스트림 파서(바이트 슬라이스·스트림 입력, wasm 에서도 동작), 청크 직렬화 |
| `pointblitz-native` | winit 창, 입력, 프레임 타이밍 |
| `pointblitz-web` | wasm-bindgen API, JS 에서 부르는 얇은 래퍼 |
| `pointblitz-server` | 헤드리스 렌더, 하드웨어 인코딩(NVENC), 영상·입력 전송 |
| `pointblitz-bench` | 시나리오 재생기, 지표 수집, 비교표·비용 모델 생성 |
| `baseline/three` | 기존 방식 재현(three.js). 비교 전용, 라이브러리에 포함하지 않는다 |
| (뒤) `pointblitz-py` | pyo3 바인딩 |

skyrecon 과의 관계: `skyrecon-core` 의 PLY·기하 타입을 쓰거나 맞춘다. 단 `read_ply` 는 파일 경로 기반이라
wasm·스트림 입력용 파서는 `pointblitz-io` 에 따로 둔다.

### 3.2 렌더링 방식

- 점은 불투명하게 그리고 깊이 버퍼로 가린다. **정렬이 필요 없다**(가우시안 스플랫과 다른 점).
- 점 하나 = 화면 정렬 사각형 또는 원. 크기는 거리와 화면 해상도로 정한다(고정 픽셀 크기 옵션 포함).
- 법선은 조명·방향 컬링 옵션에 쓴다. 기본은 색만으로 그린다(원본 three.js `Points` 와 같은 조건으로 비교하기 위해).
- 큰 장면은 청크 단위 옥트리로 절두체 컬링하고, 멀리 있는 청크는 표본만 그린다(LOD).

### 3.3 서버 ↔ 클라이언트가 주고받는 것

| 경로 | 서버가 하는 일 | 클라이언트가 받는 것 |
|---|---|---|
| 기존 방식 | PLY 파일 정적 서빙 | 이벤트마다 전체 PLY |
| 브라우저·네이티브 | PLY 를 GPU 형식 청크로 바꿔 둔다. preview 는 새 점만, refined 는 전체 교체 청크 | GPU 버퍼에 바로 올릴 수 있는 바이너리 청크(대역폭 제약 없음 → 압축하지 않고 GPU 레이아웃 그대로 보내 해석 비용 0 을 노린다) |
| 서버 영상 | 서버 GPU 가 그리고 인코딩 | H.264/HEVC 영상 프레임. 클라이언트는 재생과 입력 전송만 |

## 4. 측정

### 4.1 시나리오

- S-replay: 스냅샷 14개를 원래 시각(또는 배속)대로 순서대로 도착시킨다.
- 고정 시점 8곳(기존 연구 리포의 방법을 이어 쓴다)에서 카메라를 돌린다.

### 4.2 지표

| 지표 | 정의 |
|---|---|
| 전송 바이트 | 이벤트별·전체 |
| 이벤트 반영 시간 | 이벤트 도착 → 그 점이 화면에 나온 첫 프레임 |
| 첫 화면 시간 | 접속 → 첫 점이 그려진 프레임 |
| 프레임 시간 | p50 / p95 / p99 (GPU·CPU 따로) |
| 메모리 | CPU(프로세스·JS 힙), GPU 버퍼 |
| 메인 스레드 블록 | 50 ms 넘는 작업 수와 합 |
| 화질 | 기준 영상 대비 SSIM(같은 데이터를 그리므로 1 에 가까워야 한다. 서버 영상은 인코딩 손실 측정) |
| 서버 영상 전용 | 인코딩 시간, 비트레이트, 입력 → 화면 지연 |

### 4.3 하드웨어 비용 모델

단계별 비용을 하드웨어 독립 양으로 적는다.

| 단계 | 비례하는 양 | 좌우하는 하드웨어 값 |
|---|---|---|
| 전송 | 바이트 | 네트워크 대역폭 |
| 해석 | 바이트·점 수 | CPU 단일 스레드 성능(기존 방식) / 0(GPU 형식 그대로) |
| 업로드 | 바이트 | PCIe·메모리 대역폭 |
| 컬링·LOD | 청크 수 | GPU 연산 |
| 래스터 | 그려진 점 수 × 점 크기(픽셀) | GPU 정점 처리량·필레이트 |
| 인코딩(서버) | 해상도 × fps | 인코더 처리량 |

V100·RTX 4070 에서 잰 값으로 계수를 맞추고, 다른 GPU 는 공개 사양(메모리 대역폭, FP32 연산량, 필레이트)으로 추정한다.
V100 은 디스플레이가 없으므로 네이티브 창 대신 헤드리스 측정만 한다.

## 6. 이전 리포에서 가져오는 지식

- 좌표·투영 규약(카메라 x 오른쪽·y 아래·z 앞, GL 변환 `diag(1,−1,−1)`, 픽셀 중심 i+0.5).
- ENU(1 unit = 1 m). 씬 규약 변환은 명시적으로 한 곳에서만 한다.
- 고정 시점 8곳, SSIM 방법(Wang 2004, 11×11 가우시안 σ1.5).
- 지표 기록 형식 `{metric, value, unit, device, method, commit, samples}`.
- 원본 skylens 대조 결과(관제탑 기능 목록, 수준 교체 규칙) — 메시 단계에서 쓴다.

## 7. 열린 질문

1. **refined 스냅샷이 전부 바뀌는 이유.** 정렬 변환(Sim3)만 바뀐 것이라면 "변환 + 새 점" 으로 보낼 수 있다.
   다시 조밀화한 것이라면 전체 교체가 맞다. skyrecon 은 구역별 파일(`full/{preview,refined}/…_KK_pos….ply`)도
   내므로 구역 단위 교체가 가능한지 skyrecon 쪽과 확인이 필요하다.
2. **기존 방식의 정확한 재현.** skylens 는 지금 skyrecon 점군을 그리지 않는다. 기준을 "three.js `Points` +
   전체 PLY 다운로드 + 메인 스레드 파싱 + 이벤트마다 전체 교체" 로 잡는다(2026-10-07 합의). PLY 로더는
   three.js 기본 `PLYLoader` 를 쓴다.
3. **점 크기와 모양.** 기존 방식과 같은 화면을 내려면 three.js 쪽 점 크기 설정(`size`, `sizeAttenuation`)을 정해야 한다.
4. **서버 영상 경로의 전송 방식.** WebRTC(지연 최소) 와 WebSocket + MSE/WebCodecs(구현 단순) 중 무엇으로 할지.
